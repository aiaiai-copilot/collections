# Вычислительный стенд — PROTOTYPE

Временный исследовательский код, не реализация backend или публичного API.
Основание: [план измерений](../../docs/research/dag-navigator-scaling-experiment.PLAN.md).
Задача первого шага — проверить одинаковую семантику независимого перебора
и индексного кандидата, прежде чем сравнивать скорость.

Проверяемая граница: четыре логические возможности источника из контракта,
одна страница контрольного хоста и сборка полного ответа для обоих режимов.
Исходные данные передаются явно: синтетические элементы и сохранённые
подборки одного пространства. Нет `.env`, backend/API, сети, файловой БД,
npm-зависимостей, серверов или связи с открытым UI-прототипом.

Запуск из корня worktree (preload-настройки Node исключены):

```sh
env -u NODE_OPTIONS -u NODE_PATH node --test prototypes/dag-scaling.PROTOTYPE/rig.test.mjs
```

Тесты проверяют корректность, их длительность не является benchmark.
Случайные данные воспроизводятся по seed. Большие наборы, нагрузка,
конкурентная запись и долговечность снимков этим шагом не проверяются.

## Что реализовано

- `scan-source.mjs`: последовательный перебор; дополнительные теги
  пересчитываются независимо по словарю. Это намеренно простой, медленный
  эталон, не оптимизированный конкурент для больших нагрузок.
- `index-source.mjs`: пересечения отсортированных списков позиций элементов,
  отдельный индекс фильтров подборок, точный подсчёт тегов найденных элементов.
  Сейчас используются обычные массивы JavaScript, не компактное
  четырёхбайтовое представление из иллюстративного расчёта исследования.
- `navigation.mjs`: общий сборщик ответа по правилам Навигатора, без UI
  и истории сеанса. Обрабатывает ближайших родителей, оба режима, покрытие
  сохранённых потомков и отдельный вход в пустую сохранённую подборку.
- `contract.mjs`: общие представление, проверка фикстуры и оболочка результата;
  общих алгоритмов отбора элементов у двух источников нет.
- `small-fixtures.mjs`: ограниченный генератор, 12–60 элементов и не более
  66 подборок, фиксированный набор из шести основных тегов и два специальных.

Общая сборка навигации проверяется ручными ожиданиями и свойством достижимости
потомков. Сравнение адаптеров само по себе не является независимой проверкой
этой общей логики. Тесты не подтверждают поведение существующего UI: он
не изменялся, включая ранее отмеченное отличие пустого узла в `free`.

## Интерфейс только этого стенда

Фабрики получают `{ revision, items, nodes }` одного пространства, копируют
вход и захватывают неизменный снимок. ID — непустые строки, уникальные
внутри каждого вида записей. Неоднозначные повторные ID и одинаковые
нормализованные фильтры разных подборок отвергаются как ошибки фикстуры.
Теги уже нормализованы вызывающим кодом: стенд удаляет повторы и сортирует,
но не вводит правила регистра, Unicode-нормализации или ручного ввода.

| Операция | Результат `value` при `ok` |
| --- | --- |
| `collection(id, revision?)` | Сохранённая подборка; отсутствие даёт отдельный исход |
| `related(tags, revision?)` | Равный фильтр, все более широкие и все более узкие, не только ближайшие |
| `count(tagSets, revision?)` | Полный пакет точных AND-счётчиков в порядке запросов |
| `extraTags(tags, revision?)` | Все дополнительные теги подходящих элементов с положительными счётчиками |
| `page(tags, { offset, limit }?, revision?)` | Контрольная страница хоста и полный `total`, порядок по строковому ID |

Первые четыре операции представляют возможности источника Навигатора;
`page` добавлена для внешнего контрольного хоста, а не в его продуктовый
интерфейс. Названия методов и поля не являются согласованным публичным API.
Ответы копируются, чтобы вызывающий код не менял снимок. Копирование,
нормализация и построение индексов имеют цену: в следующем опыте учитывать
их отдельно, не выдавать загрузку данных в память за бесплатную.

`readNavigation(source, { tags?, collectionId?, mode?, revision?, offset?, limit? })`
собирает один полный ответ. Вход по `collectionId` использует фильтр найденной
подборки; вход по тегам не требует её существования. Снимок и страница
должны иметь одну ревизию. Неполный пакет счётчиков, несовпадение полного
счётчика страницы и смешанная ревизия не дают успешного ответа.
`sourceFacts` сохраняет исходные сведения для исследования; это не
проект сетевого payload и не предложение передавать их все в браузер.
Порядок вариантов детерминирован для сравнения, не воспроизводит UI-веса.

Снимок только статический. Неизвестная ревизия возвращает
`revision-unavailable`, отсутствие ID на существующей — `collection-unavailable`.
Ошибка чтения и смешанная ревизия инъецируются в тестах через интерфейс
источника. Это не проверка настоящей БД, реплик, повтора, отмены, свежести
или ограниченной пересборки при конкурентной записи. Метка фикстуры сама
по себе не является реализацией backend-ревизий.

## Зафиксированная проверка — 2026-09-23

34 теста прошли. В дифференциальном прогоне — 50 seed × 70 наборов ×
2 режима = 7000 сравнений полных навигационных ответов. Дополнительно
сверяются исходные сведения и пакетные счётчики для каждого из 3500
наборов, чтение подборок по ID, покрытие потомков и одинаковый состав
результатов в обоих режимах. Специальная фикстура из 80 независимых корней
и тегов проверяет отсутствие скрытого top-N при странице из 20 элементов.

Перед запуском проверены все импорты стенда: только относительные модули
и `node:test` / `node:assert/strict`; внешнего API target нет, `.env` не читается.
На этом малом этапе замеры производительности не выполнялись. Первый
измерительный этап добавлен отдельно, см. ниже; корректностный генератор
не увеличивается до миллионов.

## Измерительный пилот — 2026-09-23

[Отчёт первой ступени 10k](../../docs/research/dag-navigator-scaling-pilot-10k.md).
Новые файлы не меняют кандидатов, общий сборщик или UI:

- `measurement-fixture.mjs`: отдельный воспроизводимый профиль; первоначальный
  предел 100..10 000, на следующем этапе расширен только до 100 000 элементов;
  по 10 уникальных тегов, словарь по умолчанию из 1000
  возможных тегов, 100 уникальных фильтров. Ось `vocabulary: 1000|10000`
  добавлена отдельно; 10k тегов допускаются только при N<=10k.
  Фактические распределения
  и checksum записываются в результаты.
- `measurement-runner.mjs`: `runMeasuredJob(job)` запускает один изолированный
  процесс, возвращает `ok` либо явный исход ошибки/остановки. Нужны
  `candidate: verify|scan|index`, `count`, `seed`, `samples: 1..20`;
  необязательный `vocabulary` по умолчанию 1000. Недопустимое расширение
  двух осей отвергается до запуска процесса.
  Для измерения требуются `expected` — SHA-256 полных ответов отдельной
  сверки для всех сценариев задания. По умолчанию их десять; добавленный
  `queryNames` выбирает непустое окно уникальных известных сценариев в заданном
  порядке. Это разделяет запросы между процессами, не сокращает их ответы.
  Таймаут шага 30 s, процесса 120 s, наблюдаемый RSS 6 GiB,
  old space V8 4096 MiB (не весь heap/RSS), вывод 10 MiB. Раз в 250 ms читает RSS через `/bin/ps`;
  если наблюдение недоступно, не продолжает вслепую. Это не hard RSS limit.
- `measurement-worker.mjs`: строит данные и источник, сверяет либо измеряет
  до 10 сценариев, фиксирует полный цикл/стадии/CPU/память/сериализованные размеры.
  Генерация и создание источника отдельно. Вход сохраняется живым до конца,
  RSS не равен размеру индекса. Нет принудительного GC.
- `measure.mjs`: CLI только для smoke 100 и пилота 10 000; три повтора,
  по пять замеров после первого чтения и дополнительного прогрева.
  Пишет новый JSONL в `results/`, никогда не перезаписывает старый. Сохраняет
  кодовые SHA-256, профиль и окружение; останавливает серию при первой ошибке.
  При ошибке worker остаются явный исход, текущая фаза и завершённые сценарии;
  незавершённый сценарий не считается успешно измеренным.
- `measurement.test.mjs`: поведение генератора, полного задания, явная ошибка
  корректности, ресурсные ограничения; `measurement-blocked.TEST.mjs` —
  локальный занятый worker для проверки внешнего watchdog, без роста памяти.

Команды из корня worktree; для повторения нужны **новые** имена файлов:

```sh
env -u NODE_OPTIONS -u NODE_PATH node --test prototypes/dag-scaling.PROTOTYPE/rig.test.mjs prototypes/dag-scaling.PROTOTYPE/measurement.test.mjs
env -u NODE_OPTIONS -u NODE_PATH node prototypes/dag-scaling.PROTOTYPE/measure.mjs 100 smoke-new.jsonl
env -u NODE_OPTIONS -u NODE_PATH node prototypes/dag-scaling.PROTOTYPE/measure.mjs 10000 pilot-10k-new.jsonl
```

Перед запуском снова проверить ресурсы и состав entry point. Продуктовые
package scripts, `.env`, API и DSN не используются; worker получает пустое
окружение. На macOS sandbox может запретить `ps`: требуется разрешённое
read-only наблюдение собственных процессов, а не отключение watchdog.
Никакие серверы, контейнеры или БД не запускаются. Варианты `workerURL`
и `readRss` существуют для испытания внешнего процесса/OS-наблюдения;
CLI их не принимает и всегда запускает штатный worker.

Итог первой ступени: 39 тестов прошли, smoke и серия 10k завершились без ошибок; исходные
JSONL сохранены в `results/`. На одну ячейку 15 измерений, поэтому только
медиана и индивидуальные значения, без p95/p99.

## Фиксированный словарь, рост до 100k — 2026-09-23

[Отчёт второй ступени](../../docs/research/dag-navigator-scaling-growth-100k.md).
Алгоритмы обоих источников и сборщик не менялись. `measure-growth.mjs`
добавляет парное сравнение 10k/100k на seed 23, 47, 89. Независимая
сверка десяти полных ответов разделена на шесть окон: `nodes` вместе,
каждый `free` отдельно. Затем только индекс измеряется в трёх свежих
процессах, по прежним первому чтению, дополнительному прогреву и пяти
замерам каждого сценария. Медленный перебор не получает повторную
timing-серию; длительность verify не является latency запроса.

```sh
env -u NODE_OPTIONS -u NODE_PATH node prototypes/dag-scaling.PROTOTYPE/measure-growth.mjs smoke smoke-growth-new.jsonl
env -u NODE_OPTIONS -u NODE_PATH node prototypes/dag-scaling.PROTOTYPE/measure-growth.mjs growth growth-new.jsonl
```

CLI этой серии требует macOS для read-only `memory_pressure -Q` и проверяет
ресурсы перед каждой точкой: начало запрещено при неизвестном показателе,
system-wide free ниже 10% или диске меньше 1 GiB. Это исследовательская
страховка, не продуктовый лимит. Прежние timeout/RSS/old-space/output
ограничения сохранены; старые JSONL не перезаписываются.

41 тест прошёл, включая сохранение checksum первой фикстуры и корректное
покрытие выборочных окон. Серия: 54 процесса `ok`, 60 полных сравнений
источников, 900 замеров после прогрева и 180 первых чтений; на ячейку
45 наблюдений. Сырые JSONL и code SHA-256 сохранены. Индексный `free/all`:
7,33 → 40,97 ms при 1000 вариантах. Это не измерение БД/сети/записи.

Следующая ось этого этапа — словарь до 10k при фиксированных 10k элементов;
она проверена отдельной серией ниже.

## Фиксированная база, рост словаря до 10k — 2026-09-23

[Отчёт третьей ступени](../../docs/research/dag-navigator-scaling-width-10k.md).
Тот же entry point теперь поддерживает `width` и `width-smoke`: меняется
только словарь, а N=10k (smoke: 100), число назначений, сохранённые фильтры,
длины строк тегов и целевые выборки фиксированы. Частоты обычных тегов
становятся ниже, фактическое покрытие словаря записывается, а не предполагается.
Расширение V до 10k одновременно с N>10k запрещено в генераторе и runner.

```sh
env -u NODE_OPTIONS -u NODE_PATH node prototypes/dag-scaling.PROTOTYPE/measure-growth.mjs width-smoke smoke-width-new.jsonl
env -u NODE_OPTIONS -u NODE_PATH node prototypes/dag-scaling.PROTOTYPE/measure-growth.mjs width width-new.jsonl
```

Ограничения, ресурсы, порядок сверки и измерений прежние. Новый заголовок
содержит `profile.vocabularies`; записи точки имеют `count`, `vocabulary`
и `seed` — сопоставлять результаты нужно по всем трём полям. Старые JSONL
остались неизменными. Кандидаты, worker и общий сборщик не менялись.

43 теста прошли. Smoke — 14 процессов `ok`, основная серия — 54 `ok`;
60 полных сравнений источников, 900 замеров после прогрева, 180 первых чтений.
Индексный `free/all`: 7,23 → 38,88 ms; 1000 → 9999–10 000 вариантов;
итоговый JSON 126,6 KiB → 1,17 MiB. Это не измерение сети, UI или backend.
Следующий шаг — бюджет и протокол миллионной ступени, без автоматического
повышения лимитов или отказа от полной независимой сверки.

## Подготовка миллионной ступени — 2026-09-24

[Протокол допуска](../../docs/research/dag-navigator-million-admission.PLAN.md)
разделяет память индекса, копий и технических метаданных. Прямой запуск
миллиона старым заданием не допускается: независимый перебор может первым
исчерпать время, а временные копии — запас памяти. Большой прогон не выполнен;
основные генератор/runner по-прежнему ограничены 100k.

`partition-proof.mjs` — отдельная **малая проверка композиции**, максимум
100 элементов и 100 узлов. Тот же Interface источника поверх независимых
переборов непересекающихся порций: точные счётчики суммируются, все теги
объединяются, страница формируется в глобальном порядке. Полные сохранённые
подборки общие; их счётчики не складываются друг с другом. Это синхронная
проверка, удерживающая все порции, а не будущий многопроцессный runtime.
Измерять её RSS/latency как миллионный кандидат нельзя. Источники, общий
сборщик, измерительный worker, прошлые JSONL и UI не менялись.

```sh
env -u NODE_OPTIONS -u NODE_PATH node --test prototypes/dag-scaling.PROTOTYPE/rig.test.mjs prototypes/dag-scaling.PROTOTYPE/measurement.test.mjs prototypes/dag-scaling.PROTOTYPE/partition-proof.test.mjs
```

49 тестов прошли. Новые TDD-проверки и 21 000 полных сравнений на 50 малых
пространствах подтверждают композицию с размерами порций 1/7/100. Это не
проверка будущих IPC, манифестов, потокового генератора или ресурсоёмкости:
их ещё нужно реализовать/проверить до допусков 250k → 500k → 1m.
