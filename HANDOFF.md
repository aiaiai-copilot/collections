## Session 2026-09-04

### Главная задача следующей сессии

Начать отдельное концептуальное исследование **«Иерархия подборок»**, не изменяя действующую спецификацию коллекций. Использовать Wayfinder для новой карты, затем domain-modeling для отдельного словаря. Цель первой сессии — сделать новый концепт достаточно точным для сравнения с текущим, а не проектировать реализацию.

Новый концепт остаётся в этом репозитории как соседний bounded context. Отдельный Git-репозиторий преждевременен; вернуться к разделению только если оба варианта должны развиваться как самостоятельные продукты с разными релизами и минимальным общим ядром.

### Зафиксированная отправная точка нового концепта

- Выделенной «Коллекции» в текущем значении нет; центральная сущность — подборка с тег-фильтром.
- Отношение уточнения фильтров образует семантический DAG произвольной глубины: у подборки может быть несколько более широких семантических родителей.
- Для стабильной мобильной навигации поверх DAG задаётся отдельное дерево или лес: у каждой подборки не более одного явно выбранного основного родителя, совместимого с направлением уточнения фильтра.
- Хлебные крошки всегда показывают стабильную цепочку основных родителей. Альтернативные семантические родители отображаются отдельно, например как «Более общие подборки».
- Канонический URL адресует подборку по непрозрачному идентификатору и не сериализует путь; основной путь восстанавливается по основным родителям.
- Для простого пересечения тегов уточнение означает `parent.tags ⊆ child.tags`. Семантика `OR`, `NOT` и сложных фильтров пока не определена.

Канонический словарь этой альтернативы: [контекст «Иерархия подборок»](docs/concepts/selection-hierarchy/CONTEXT.md). [Карта контекстов](CONTEXT-MAP.md) отделяет его от действующего корневого `CONTEXT.md`. Не переносить новые определения в старый контекст до явного выбора концепта.

### Первый frontier новой сессии

С помощью Wayfinder назвать destination и создать отдельную карту под `.scratch/selection-hierarchy/`. Первый доменный вопрос: **что заменяет коллекцию как границу существования и владения элементом, тегов, поиска, удаления, сравнимости и общего порядка?** После ответа уточнять только ставшие видимыми вопросы; список оставшегося fog уже находится в контексте «Иерархия подборок».

Не начинать с базы данных, API или UI-макетов: пока не определена новая aggregate boundary, они закрепят случайную модель. Не изменять `.scratch/collections-product-prototype/issues/03-specify-demonstration-product.md`; это спецификация другого концепта.

### Результаты текущего основного effort

- Канонический черновик действующего продукта: `.scratch/collections-product-prototype/issues/03-specify-demonstration-product.md`.
- Сравнение Selectel, Beget и Timeweb зафиксировано в `docs/research/self-hosted-and-yandex-product-foundation.md`; Yandex Compute исключён из детальной ценовой таблицы.
- Промежуточно выбран один Beget VPS с PostgreSQL, NestJS и SPA; OpenAPI 3.1 остаётся spec-first Interface. Точное решение и условия пересмотра находятся в `.scratch/collections-product-prototype/issues/01-choose-product-foundation.md`, `Status: resolved`.
- Базовый Beget-вариант не включает warm standby или автоматический failover. Встроенные файловые бэкапы не заменяют независимый PostgreSQL base backup + WAL.

- В действующей спецификации остаются четыре открытых продуктовых решения: граница первого показа, граница тегов/формата элемента, RPO/RTO и диагностика, судьба демонстрационных данных.
