# Доступ к данным составного интерфейса

Родитель: [Верхнеуровневый интерфейс Навигатора](dag-navigator-upper-interface.DRAFT.md).
Связь: детализация — задаёт потребности и взаимодействия доступа к данным.

Статус: **потребности, единая точка настройки, четыре предметные операции, структурные запросы и логические аргументы и ответы этих операций приняты**.
Принято неблокирующее ожидание подходящих данных внутри логического
получения. Физические типы, оболочки ответов и формат конфигурации ещё не определены.
Это логический контракт, не выбор языка, структуры директорий, хранилища
или сетевого протокола. Работа ограничена одной заданной приложением
[областью данных Навигатора](dag-navigator-upper-interface.DRAFT.md#область-данных-навигатора).
Все операции рассматривают элементы, теги и записи пользовательского среза этой области. Ею
может служить коллекция или личное пространство; источник и его адаптер
не определяют продуктовую модель владения элементами.

`selection` обозначает запись пользовательского среза, `collection` — продуктовую коллекцию. [Словарь имён контракта](dag-navigator-upper-interface.DRAFT.md#английские-имена-понятий).

Основания: [DIP и возможности источника](dag-navigator-contract.DRAFT.md#2-данные-на-входе),
[условия начала работы](dag-navigator-upper-interface.DRAFT.md#начало-работы),
[согласованная сборка](coherent-result-contract.DRAFT.md),
[связь с выдачей](results-view-contract.DRAFT.md#область-ответственности).

## Участники взаимодействия

Приложение — пользовательский продукт в целом, включая разрабатываемый
составной модуль. Настройку и вызовы его верхнего интерфейса выполняет
использующий код приложения: экраны и прикладные сценарии. Эти выражения
не обозначают разные процессы или стороны frontend/backend.

В составном модуле разделены DAG-навигация, выдача, история и координация.
Адаптеры связывают необходимые им возможности с конкретной системой данных.
Редактирование и сохранение элементов находятся вне рассматриваемого модуля.

Направление зависимостей определяет
[правило интерфейсов окружения](dag-navigator-contract.DRAFT.md#интерфейсы-и-адаптеры-окружения):
контракты задаются со стороны Навигатора, адаптеры конкретного окружения
зависят от них согласно DIP. Это относится и к связи с приложением,
не только к источнику данных; сами приложение и источник — не адаптеры.

## Принятые потребности

Использующий код приложения настраивает доступ к необходимым данным через адаптер,
не передаёт всю базу. Четыре возможности источника DAG приняты ранее;
получение страницы требуется составному интерфейсу, но не становится
пятой обязанностью предметной логики DAG.

| Логическая возможность | Вход по смыслу | Необходимые сведения | Кто использует |
| --- | --- | --- | --- |
| Получить пользовательский срез по ID | ID | Сведения о пользовательском срезе, его исходной области и фильтре либо недоступность | DAG-навигация |
| Получить связанные записи пользовательского среза | Произвольный набор тегов | Записи пользовательского среза с равным, более широкими и более узкими фильтрами | DAG-навигация |
| Получить количества | Один или несколько наборов тегов | Число уникальных подходящих элементов для каждого AND-фильтра | DAG-навигация и выдача |
| Получить теги подходящих элементов для уточнения фильтра | Заданный фильтр | Теги, ещё не включённые в фильтр, и число результатов при добавлении каждого из них отдельно | DAG-навигация |
| Получить страницу элементов | Заданная выборка и параметры выдачи | Элементы запрошенной области и параметры, которым соответствует ответ | Общая выдача |

имя операции получения страницы и число сетевых запросов здесь не задаются.
В общем контракте выдачи принято [единое получение страницы](results-view-contract.DRAFT.md#получение-страницы-без-отдельного-поиска-позиции)
для обычного перехода и восстановления места, без обязательного отдельного
метода поиска позиции. Принятая гарантия запасного поиска сохраняется.
Общее количество текущей выборки можно переиспользовать между потребителями;
таблица не требует повторного подсчёта или двух публичных копий количества.
Форма карточки элемента и физическое представление ссылок на теги ещё
уточняются. Логические поля четырёх DAG-операций приняты ниже.

доступ принято ниже.

Эта таблица описывает получение данных для согласованного результата.
Настроенный доступ также предоставляет принятую возможность
[преобразования введённых названий в ссылки](#преобразование-введённых-названий-в-ссылки).
Она обслуживает подготовку ручного ввода, а не добавляет ещё один вид
перехода DAG. Преобразование не требуется перед каждой навигацией по уже
готовым ссылкам или вариантам перехода.

Свободный режим использует произвольный набор тегов, даже без ID записи пользовательского среза.
Он соединяет дополнительные теги элементов с данными об уточняющих
записях пользовательских срезов. Источник не обязан заранее перечислять все промежуточные узлы.
Навигатор определяет ближайших родителей, уточнения и покрытие вариантов;
адаптер предоставляет данные и вычисления по контракту, а не выбирает
показываемые варианты по собственной политике.

Выдача работает с уже заданной выборкой. Для текущего применения это
AND-фильтр; общий модуль выдачи не обязан знать о родителях DAG, режиме
«Узлы»/«Свободно» или истории посещений. Способ указания страницы, порядок,
размер и получение места по элементу остаются вопросами общего контракта
выдачи, а не новыми навигационными действиями.

## Именованные предметные операции

Четыре возможности DAG-доступа выражаются отдельными именованными
логическими операциями. На этом шаге приняты группировка и имена;
аргументы и поля ответов приняты последующими решениями ниже.
Обязательное число сетевых обращений не задаётся.

| Принятое имя | Принятая задача и сведения |
| --- | --- |
| `readSelection` | По ID получить сведения о пользовательском срезе, его исходной области и фильтре либо установленную недоступность |
| `readRelatedSelections` | Для заданного фильтра получить сведения о связанных записях пользовательских срезов: с равным, более широкими и более узкими фильтрами |
| `countMatches` | Для пакета фильтров получить число уникальных подходящих элементов по каждому фильтру |
| `readRefinementTagsFromItems` | Получить теги подходящих элементов, ещё не включённые в заданный фильтр, и число результатов при добавлении каждого из них отдельно |

`RefinementTags` указывает назначение тегов — уточнение фильтра; `FromItems` — их источник, подходящие элементы. Ответ включает количество результатов при отдельном добавлении каждого тега.

Эти операции использует внутренняя логика Навигатора через настроенный
адаптер. Обычное приложение продолжает вызывать `select`, операции изменения
фильтра и `setMode`, а не вручную собирать навигационный результат.
Условия согласованного чтения относятся к общему получению и не становятся
новыми пользовательскими аргументами; способ их передачи пока не выбирается.

Четыре логические операции не требуют четырёх сетевых запросов на каждый
переход или повторения всей работы. Реализация может переиспользовать данные,
совмещать вычисления и объединять технические обращения при сохранении
контракта. Это не гарантия эффективности: стоимость будет зависеть от
области запроса, объёма данных и выбранной реализации. Пакет количеств
не требует отдельного публичного вызова для каждого варианта.

Аргументы, логические поля ответов и область запроса связанных записей пользовательских срезов
конкретизированы ниже. Принятие группировки само по себе не вводит обязательную
выгрузку всего каталога или всех связанных записей пользовательских срезов. Принятые требования
полноты выбранной задачи и определения переходов самим Навигатором сохраняются.
Страницы, ручной ввод и глоссарий остаются отдельными частями доступа;
четыре операции не объявляются всем интерфейсом составного модуля.

## Точные предметные выборки и сводные сведения

Для `readRelatedSelections` не закрепляется единственный вариант
«вернуть все связанные записи пользовательского среза». Навигатор может запрашивать точные
предметные выборки и сводные сведения по определённым им правилам;
адаптер может выполнять соответствующие структурные вычисления.
Принят принцип распределения обязанностей, а не точные поля запросов
и ответов или произвольная политика выбора переходов адаптером.

Основание: для пустого фильтра все непустые сохранённые фильтры являются
более узкими. Поэтому полный список потомков в этом случае — почти весь
каталог, а вместе с равным фильтром — весь каталог. Получение только ближайших
записей пользовательских срезов также недостаточно для свободного режима: он использует теги
всех уточняющих записей пользовательских срезов, включая более глубокие и имеющие нулевой результат.

Например, для текущего `{фильм}` сохранены `{фильм, спокойное}` и
`{фильм, спокойное, вечер}`. Даже если у элементов текущего среза нет тега
`вечер`, он участвует в однотеговых уточнениях свободного режима благодаря
второй записи пользовательского среза. Список только ближайших уточняющих записей пользовательских срезов его потеряет.
Источником тега является глубокая запись пользовательского среза, но ближайшим целевым узлом
свободного перехода будет `{фильм, вечер}`, а не сама эта запись пользовательского среза.
При согласованных данных тег, добавляемый только вторым источником,
даёт нулевой результат: если бы он встречался у подходящего элемента,
его уже предоставил бы первый источник. Это не означает, что каждая
пустая запись пользовательского среза обязательно добавляет новый вариант.

В следующей конкретизации нужны точные сведения для разных задач:

- все записи пользовательского среза с фильтром, в точности равным заданному;
- все ближайшие более широкие и более узкие записи пользовательского среза по включению тегов;
- объединение дополнительных тегов всех уточняющих записей пользовательских срезов для свободного режима;
- сведения, достаточные для принятых правил покрытия вариантов, если они
  не выводятся из остальных ответов.

Адаптер выполняет структурные вычисления по контракту Навигатора согласно DIP. Навигатор задаёт смысл запроса и состав показываемых переходов; адаптер исполняет точный запрос без эвристического отбора или скрытого лимита.

Преимущество относительно обязательной передачи всех исходных записей —
можно не передавать глубокие записи пользовательского среза целиком, когда достаточно точной сводки.
Компромисс — интерфейс и реализация доступа должны поддерживать больше
структурных вычислений. Это не гарантия малых ответов: самих ближайших узлов
или различных тегов может быть много, а вычисления имеют стоимость.
Полнота и согласованность данных сохраняются. Точный состав запросов/ответов
и достаточность для всех принятых правил ещё требуют сверки; новая сигнатура,
новый метод, размещение по стеку и численные пределы здесь не утверждаются.

## Запрашиваемые части связанных сведений

Точное совпадение полного фильтра в заданной области данных может соответствовать нескольким пользовательским срезам. Все совпадения предоставляются без выбора одной записи. Ближайшие расширения и уточнения предоставляются отдельными частями ответа.

Внутри `readRelatedSelections` передаются полный нормализованный `filter` и непустой набор
`requestedParts` — имён требуемых частей ответа. Для одного фильтра
можно запросить одну или несколько частей. Общие условия согласованного
чтения сохраняются; это предметная часть обращения, не его полный
технический формат и не новое действие приложения.

| Имя части | Смысл успешного ответа |
| --- | --- |
| `sameFilterSelections` | Все доступные пользовательские срезы той же области с точно таким же полным фильтром; пустой список означает отсутствие совпадений |
| `nearestBroaderSelections` | Все ближайшие сохранённые записи пользовательского среза со строго более широкими фильтрами |
| `nearestNarrowerSelections` | Все ближайшие сохранённые записи пользовательского среза со строго более узкими фильтрами |
| `selectionRefinementTags` | Все ещё не выбранные теги из фильтров всех строго уточняющих сохранённых записей пользовательских срезов, без повторений |

Ответ содержит запрошенные части; отсутствие незапрошенной части не
используется как утверждение об отсутствии данных. Успех означает
полноту всех запрошенных частей по общим условиям чтения. Это выбор
объёма внутреннего запроса, а не выдача приложению частичного результата.

Например, при `filter = {фильм}` сохранённая запись пользовательского среза «Фильмы» с таким же фильтром входит в `sameFilterSelections`. Запись пользовательского среза `{фильм, комедия}` входит в `nearestNarrowerSelections`, если между ними нет сохранённого строго промежуточного фильтра. `selectionRefinementTags` содержит объединение тегов всех строго уточняющих записей пользовательских срезов.

Сравнивается полный набор ссылок на теги в одной исходной области, а не название, порядок тегов или состав элементов. `sameFilterSelections` содержит все совпадения, включая несколько записей с одинаковым фильтром. Порядок выдачи не участвует в распознавании. Сведения о пользовательском срезе включают ID, название, область и фильтр; форма передачи области ещё требует определения. Успешный ответ без совпадений отличается от сбоя получения и недоступности записи при поиске по ID. `readSelection` выполняет поиск по ID.

Ближайшие записи пользовательского среза определяются отсутствием сохранённой записи пользовательского среза
со строго промежуточным фильтром. Количество элементов не исключает
запись пользовательского среза из этих ответов или из источника `selectionRefinementTags`.
Теги подходящих элементов предоставляет `readRefinementTagsFromItems`;
источники свободных уточнений не смешиваются в новое значение операции.
При `filter = []` список точных совпадений содержит все доступные
пользовательские срезы той же области с пустым фильтром. Само получение
этих сведений не переводит положение «Всё» ни в одну из записей.

Приняты имена и группировка предметных частей, а не
JSON, кодирование отсутствия, физические типы или отдельные сетевые
запросы. Принцип позволяет не вычислять и не передавать ненужные части;
эффективность конкретной реализации отдельно проверяется.
Достаточность для базовой навигации проверена ниже. Это не обещание
исчерпывающих данных для любого дополнительного потребителя.
Представление записей пользовательских срезов и ошибки неверного запроса уточняются
отдельно; новые публичные причины отказа здесь не вводятся.

### Сверка достаточности для навигации

Части связанных сведений вместе с `readRefinementTagsFromItems`, `countMatches` и поиском по ID обеспечивают предметные сведения базовой навигации в согласованном состоянии данных:

- точное совпадение даёт все пользовательские срезы текущих области и фильтра;
- ближайшие сохранённые подмножества дают все варианты расширения
  режима записей пользовательских срезов, ближайшие надмножества — его обычные уточнения;
- свободные уточнения образуются объединением тегов подходящих элементов
  и `selectionRefinementTags`, добавлением каждого тега к текущему фильтру;
- записи пользовательского среза с точно совпадающим фильтром свободной цели доступны через
  `sameFilterSelections`.
  Если запрошены ближайшие уточняющие записи пользовательского среза, этого списка тоже достаточно:
  между фильтрами, отличающимися одним тегом, строгого промежуточного
  фильтра нет. Способ переиспользования и пакетирования не предписывается;
- количества для текущего фильтра и целей доступны через ранее принятые
  операции; список карточек элементов для этих вычислений не требуется.

Достижимость всех сохранённых уточняющих записей пользовательских срезов не требует передачи
ID каждого покрываемого потомка. Для любого потомка `S` текущего `Q`
в конечном каталоге есть ближайшая сохранённая цель `M`, где
`Q ⊂ M ⊆ S`; сохранение всех ближайших целей обеспечивает первый шаг
в режиме записей пользовательских срезов. В свободном режиме объединение тегов содержит каждый
тег из `S \ Q`; добавление любого из них даёт первый шаг с фильтром,
остающимся подмножеством `S`. Повторение правила сохраняет путь до `S`.
Нулевое количество элементов не меняет рассуждение. Это проверка принятого
[правила достижимости](dag-navigator-contract.DRAFT.md#5-результаты-варианты-перехода-и-ввод),
а не предложение ограничить набор целей.

Представление порядка выдачи и его применение при открытии записи пользовательского среза требуют определения в [открытой части контракта](dag-navigator-upper-interface.DRAFT.md#учёт-заданного-порядка-открытая-часть-контракта).

Сведения для явного входа из «Всё» в именованную запись пользовательского среза с пустым фильтром доступны через `sameFilterSelections` при `filter = []`. Этот вход не является строгим уточнением и не заменяет однотеговые уточнения свободного режима.

Списки `coveredNodeIds`, число сохранённых потомков каждого перехода
и полный диагностический снимок из этих частей в общем случае
не восстанавливаются. Базовые поля [варианта перехода](dag-navigator-result-schema.DRAFT.md#целевой-узел-и-количество-в-варианте-перехода)
их не требуют; дополнительная диагностика остаётся опциональной.
При необходимости воспроизвести такую диагностику или вторичную сортировку
по числу потомков понадобятся дополнительные сведения.
Сверка подтверждает предметную достаточность, а не производительность,
реализацию всех UI-состояний или гарантию маршрута при произвольных изменениях данных.

## Единые записи и формы остальных операций

Приняты следующие логические имена аргументов и сведений. Смысл операций сохраняется.

| Операция или запись | Принятая форма |
| --- | --- |
| Сведения о пользовательском срезе | `id`, `name`, `filter` в заданной исходной области; одна смысловая форма для поиска по ID и связанных записей. Способ передачи области требует определения; собственного ручного порядка у записи нет |
| `readSelection` | Аргумент `id`; ответ — сведения о записи пользовательского среза либо установленная недоступность выбранной по ID записи пользовательского среза |
| `countMatches` | Аргумент `filters`; для каждого запрошенного полного фильтра — соответствующее количество `total` |
| `readRefinementTagsFromItems` | Аргумент `filter`; ответ — записи `tag`, `total`: тег подходящих элементов, ещё не включённый в фильтр, и число результатов при его добавлении |

`filter` — полный нормализованный AND-набор ссылок на теги; `tag` — ссылка
на один тег, не его отображаемое название. `total` — количество уникальных
подходящих элементов. В `readRefinementTagsFromItems` оно относится к полному
фильтру после добавления тега, не к глобальной частоте тега. Каждый тег
рассматривается отдельно как добавление к исходному фильтру; получение
этих сведений само по себе не меняет выбранный пользователем фильтр.
Однозначное соответствие количеств фильтрам обязательно по ранее принятому
правилу; копировать фильтр в каждый ответ не требуется. Например, связь
может обеспечиваться контекстом запроса — конкретный механизм не выбран.

Технический сбой не представляется нулём, пустым набором или установленной
недоступностью. Физическое кодирование недоступности, оболочка ответа,
типы идентификаторов и правила некорректных аргументов этим решением
не выбираются. Поле `total` согласовано по имени со счётчиком элементов
в уже принятом варианте перехода; это не обязательное дублирование
количества в нескольких частях результата.

## Логический граф и его представление

«узел» относится к предметной модели,
а не требует заранее созданной записи в хранимом графе. Отношение
«шире → уже» определяется включением наборов тегов. Это определённая
семантика, а не предположение о способе хранения данных.

Запись пользовательского среза — сохранённый объект с ID. Промежуточный узел задаётся непустым
фильтром без соответствующей записи пользовательского среза; для выбора такого среза не требуется
создавать запись пользовательского среза или сохранять отдельный объект графа. Источник не обязан
предварительно перечислять все промежуточные узлы и связи.

Связи можно вычислять по запросу, хранить заранее или частично сохранять
для ускорения. Конкретный способ не выбран: он не меняет смысл операции,
но влияет на стоимость, производительность и масштабируемость. Контракт
не требует материализованного графа и не запрещает его использование.
Принятые различия «Всё» и именованной записи пользовательского среза с пустым фильтром сохраняются.

модель можно понимать
как неявный, виртуальный DAG тег-фильтров. Узлами являются фильтры,
а не элементы. При добавлении тега `t` к текущему набору `Q` целевой фильтр
равен `Q ∪ {t}`; если ему не соответствует сохранённая запись пользовательского среза, он задаёт
промежуточный узел, а не требует создания отдельной сущности.

Предлагаемые однотеговые уточнения используют два принятых источника:
дополнительные теги подходящих элементов и теги фильтров уточняющих
сохранённых записей пользовательских срезов. Речь обо всей текущей выборке, не только о показанной
странице. Это не требование загрузить все элементы для вычисления вариантов.
Данные определяют доступные предложения и количества; отношение уточнения
определяется включением наборов тегов. Модель не ограничивается сочетаниями
с непустым результатом: допустимый ручной фильтр и сохранённая запись пользовательского среза
могут не иметь подходящих элементов. Перечисление всех сочетаний и
предварительная сборка полного графа не требуются.

описанные выше правила или текущие требования к доступу.

## Возможность оптимизации сохранённых записей пользовательских срезов

Сохранённая запись пользовательского среза
с идентичностью и заданным фильтром — заранее известный объект повторного
использования. Это позволяет рассматривать целевую подготовку и повторное
использование структур, ускоряющих работу с ней, например индексацию.
Значение записи пользовательского среза для архитектуры не ограничивается наличием названия.

Это предпосылка для проектирования, не обязательство публичного контракта
индексировать каждую запись пользовательского среза и не обещание производительности. Промежуточные
узлы тоже могут использовать общие индексы и другие способы ускорения;
различие — в наличии заранее сохранённой цели для целевой подготовки,
а не в исключительном праве записей пользовательских срезов на оптимизацию.

При выборе реализации нужно сопоставлять выигрыш чтения со стоимостью
подготовки, хранения и обновления при изменении элементов, тегов или фильтра.
Оптимизация не меняет выбранный фильтр и принятые гарантии согласованности:
совпадения ID недостаточно, если фильтр записи пользовательского среза уже изменился. Наличие
`selection` в результате не означает готовности специального индекса.

Конкретные структуры, выбор оптимизируемых записей пользовательских срезов и размещение вычислений
сейчас не выбираются; обязательные публичные команды управления индексами
не вводятся. Предполагаемый выигрыш требует отдельной проверки для выбранной
реализации. Новых замеров или изменения выводов завершённого ограниченного
исследования эта запись не означает.

## Предметные сведения: сверка принятого

Таблица определяет логический состав данных; физическая вложенность и сигнатуры требуют определения.

| Сведения | Уже принятый состав и смысл |
| --- | --- |
| Пользовательский срез | ID, название, исходная область и AND-фильтр из ссылок на теги. Один смысл описания используется при поиске по ID и относительно текущего набора; форма передачи области требует определения |
| Связанные записи пользовательского среза | Сведения относительно заданного фильтра по правилам Навигатора; адаптер может выполнять точные структурные вычисления. [Именованные части запроса и ответа](#запрашиваемые-части-связанных-сведений) приняты |

| Дополнительный тег подходящих элементов | Ссылка на ещё не выбранный тег и количество для полного набора после его добавления: для текущего `Q` и тега `t` — количество для `Q ∪ {t}`, не глобальная частота `t` |

Основания: [возможности источника](dag-navigator-contract.DRAFT.md#2-данные-на-входе),

записях пользовательских срезов: свободный режим использует оба источника вариантов. Для перехода
с добавлением нескольких тегов требуется количество полного назначения;
суммировать однотеговые количества нельзя. Нулевое количество — данные,
не отсутствие ответа и не основание автоматически скрыть сохранённую

## Фильтр с недоступным тегом

Рассматривается случай, когда
источник установил: фильтр с конкретной ссылкой на тег больше нельзя
обслужить по действующей модели данных. Это не отсутствие элементов,
не невозможность сопоставить новый текст и не технический сбой проверки.
Правило нужно для произвольно заданного фильтра, восстановленного выбора
и фильтра сохранённой записи пользовательского среза, а не только для ручного ввода.

Сохраняем выбранный набор и явно сообщаем о недоступности
выборки, не ослабляя её условие ради получения ответа:

- Не снимать недоступный тег автоматически и не подменять его другим
  по совпадению отображаемого названия.
- Не представлять невозможность обслужить фильтр как успешную пустую
  выборку с количеством `0`.
- Не выдавать старый комплект за результат нового успешного получения.
  Ранее доступные данные подчиняются общим правилам отображения прежнего
  комплекта, а не становятся ответом для новых данных.
- Для исправления пользователь может явно задать другой полный набор
  либо выбрать «Всё». Предусловия относительной команды снятия тегов
  этим решением не меняются.

Пример: выбран `{фильм, спокойное}`. Если источник подтверждает, что ссылку
на `спокойное` больше нельзя использовать в фильтре, не переключаем выбор
на `{фильм}` и не объявляем, что спокойных фильмов ноль. Сообщаем, что
заданную выборку сейчас нельзя получить; исправление набора остаётся явным
действием пользователя.

Само отсутствие записи в глоссарии ещё не универсальный признак такого
исхода. Если модель допускает данный тег как значение фильтра и источник
может точно вычислить состав, действует обычное получение, в том числе
с нулём элементов. Если проверка завершилась техническим сбоем,
недоступность тега не считается установленной.

В логическом каталоге чтения этот случай обозначен как «Фильтр недоступен».
Он отличается от недоступности записи пользовательского среза по ID: допустимый фильтр может
существовать без записи пользовательского среза, а доступная по ID запись пользовательского среза может содержать тег,
который больше нельзя использовать. Машинное имя исхода доступа и его
физический формат ещё не выбраны.

[Сопоставление с итогами команд](dag-navigator-actions.DRAFT.md#недоступный-фильтр-и-итог-команды)
использует существующий `target_unavailable`, не новый публичный код.
Отображение недоступных тегов и политика удаления/объединения глоссария
остаются открытыми. Новых полномочий менять сохранённые записи пользовательского среза
или глоссарий у Навигатора не появляется.

## Согласованность — общая обязанность

Источник обеспечивает согласованность связанных сведений на общей ревизии
и учёт требуемых сохранённых изменений как условия успешного получения.
Координатор сопоставляет ревизии и условия успешных обращений с требованиями
цикла, проверяет полноту и пригодность текущему запросу, затем согласованно
применяет комплект. Он не повторяет проверку учёта правок у источника
или вычисления родителей/количеств. Обычное приложение не собирает ответы
по ревизиям вручную.

Если данные поступают несколькими ответами, одинаковая метка на несвязанных
состояниях не делает их согласованными. Если источник отдаёт всё необходимое
сразу, искусственно дробить получение не требуется. Эти гарантии относятся
к данным независимо от числа объектов, процессов, хранилищ и обращений.

Внутренние исходы источника различаются: полный ответ, недоступность
записи пользовательского среза по ID, недоступность фильтра, недоступность ревизии, несовместимость условий чтения,
ошибка чтения. Ожидание учёта
сохранённых изменений также не смешивается с ошибкой. Их точные формы
ещё открыты; это не дополнительные значения публичного `kind`.
Ограниченная пересборка и сопоставление с принятыми
[публичными причинами](dag-navigator-actions.DRAFT.md#публичные-причины)
остаются внутри выполнения с учётом смысла конкретной операции.

## Логический состав обращения

Здесь описан обмен внутренних модулей с настроенным доступом к данным,
не новые аргументы пользовательских команд. Использующий код приложения
выбирает цель через верхний интерфейс; ревизии и сборку частей
ему передавать вручную не требуется.

В обращении различаются две группы сведений:

| Группа | Содержание |
| --- | --- |
| Задача получения | Какие сведения нужны и для чего: ID записи пользовательского среза, один или несколько наборов тегов либо выборка с параметрами выдачи |
| Условия чтения | Требуемая ревизия, когда она задана для согласованного чтения; требование учёта сохранённых изменений, когда оно предъявлено этому получению |

Для получения данных согласованного результата состав задачи определяется
пятью возможностями в таблице выше. Подготовка ручного ввода описана
отдельно и не приравнивается к получению готового результата навигации. Условия
чтения общие для предметных данных и страницы; они не являются спецификой
DAG. Это логические сведения, не требование двух буквальных полей,
обязательного токена в каждом вызове или отдельного метода подготовки.

Ревизия отвечает за одно согласованное состояние данных. Требование учёта
изменений отвечает за то, какие известные сохранения должны быть отражены.
Ни одно не заменяет другое. Для заданной ревизии сохраняется запрет молча
перейти к другой. Когда ревизия ещё не определена, её выбор остаётся
за согласованным получением; обязательный порядок «первое/следующие чтения»
не вводится. Общая область подтверждения изменений и способ передачи
оснований ещё требуют конкретизации.

Экземпляр Навигатора, история посещений, состояние панели и смысл режима
не требуются источнику для выполнения этих задач. Связь ответа с текущей
целью и попыткой проверяется внутри составного модуля. Это не запрещает
техническое связывание запросов и ответов, но не требует серверной сессии
Навигатора или переноса правил выбора переходов в адаптер.

## Состав ответа и граница завершения

Успешный ответ предоставляет данные запрошенной области. Выполнение
предъявленных условий, включая требуемый учёт изменений, гарантируется
самим успехом; [отдельное подтверждение не требуется](coherent-result-contract.DRAFT.md#успешный-ответ-и-условия-чтения).
Необходимая фактическая ревизия известна из ответа или общего контекста.
Связь с запросом может обеспечиваться самим способом обращения;
повторять аргументы в теле ответа не требуется. Обязательная служебная
группа «основание чтения» не вводится; машинные поля ещё не выбраны.

Полнота относится к конкретной задаче получения, не ко всему результату
Навигатора. Готовая страница ещё не означает готовности переходов и счётчиков.
Успешный ответ источника не равен `succeeded` верхнего обращения: общую
готовность и применимость комплекта проверяет координатор.

### Сверка состава обмена

Сверка документальная, без реализации. Для пяти возможностей доступа
достаточны уже описанные задача и условия чтения; вводить ID экземпляра
Навигатора, историю или состояние UI в предметные аргументы не требуется.

| Проверяемый случай | Следствие принятых правил |
| --- | --- |
| Запись пользовательского среза открывается по ID | Фильтр берётся из данных той же ревизии, на которой согласуется остальное чтение; ID сам по себе не фиксирует фильтр навсегда |
| Выбор задан произвольными тегами | Отсутствие сохранённой записи пользовательского среза с таким фильтром не препятствует получению вариантов, количеств и страницы |
| Части имеют разные ревизии | Их нельзя применить как согласованный комплект; молчаливая замена запрошенной ревизии запрещена |
| Страница успешно получена с требованием учесть X, счётчики ещё не получены с соответствующими условиями | Успех страницы не делает готовым весь комплект; отдельный флаг учёта X не требуется |
| Получены дополнительные уведомления во время чтения | Они не меняют зафиксированное требование начатого цикла; ранее принятые правила последующей актуализации сохраняются |
| Экземпляр завершён во время чтения | Ожидающее верхнее обращение получает `cancelled`, потребность в чтении прекращается; поздний ответ не возобновляет экземпляр |

Новых гарантий или выбранных полей эта сверка не вводит. Успех гарантирует
условия обращения; координация проверяет пригодность совокупности ответов.

### Ожидание внутри логического получения

применяется общее правило
[неблокирующего ожидания данных](coherent-result-contract.DRAFT.md#неблокирующее-ожидание-данных).
Временное отставание обрабатывается внутри согласованного доступа,
а успешный ответ уже удовлетворяет предъявленным условиям. Вызывающий
модуль не обязан получать «ещё не готовы» и организовывать повторное
обращение. Такой ответ допустим между внутренними частями реализации,
не как обязательный исход этого логического получения.

Сохраняются следующие смысловые различия завершённых ответов; точные
машинные имена и физические формы ещё не выбраны:

| Логический исход | Определение |
| --- | --- |
| Данные получены | Получен полный ответ для заданной задачи и условий чтения |
| Запись пользовательского среза недоступна | Запрошенная по ID запись пользовательского среза недоступна |
| Фильтр недоступен | Заданный фильтр недоступен |
| Ревизия недоступна | Источник не может обслужить заданную ревизию |
| Условия чтения несовместимы | Предъявленные требования не могут быть выполнены одновременно |
| Ошибка чтения | Произошёл сбой получения данных |

[Недоступность фильтра](#фильтр-с-недоступным-тегом) установлена, когда
источник подтверждает невозможность обслужить его по действующей модели
тегов. Ноль совпадений, технический сбой и временное отставание данных
сами по себе этого исхода не означают.

[Несовместимость условий принята](coherent-result-contract.DRAFT.md#несовместимость-условий-чтения)
как отдельный исход при установленном противоречии. Проверки могут
распределяться между участниками реализации; потребитель не обязан
самостоятельно повторять диагностику. [Восстановление выбором другой
ревизии](coherent-result-contract.DRAFT.md#пересборка-при-неподходящей-ревизии)
принято для устранимого внутреннего выбора, с сохранением задачи/требований
и общим конечным пределом с пересборками из-за недоступности ревизии.
[Публичный итог неустранённого внутреннего конфликта](coherent-result-contract.DRAFT.md#итог-неустранённого-внутреннего-конфликта)
принят как `failed / execution_error` для корректной исходной задачи.
Отдельный внутренний исход несовместимости сохраняется.

Документальная сверка исходов: пустой корректный ответ является данными;
отставание при достижимых условиях — ожиданием; недоступность ревизии
или ошибка проверки не доказывают конфликт требований. Определение причины,
передача исхода и выбор восстановления не обязаны выполняться одним
участником. Эта сверка не выбирает приоритет нескольких одновременно
установленных причин или новые публичные коды.

Отсутствие совпадающей записи пользовательского среза при запросе по тегам и нулевое количество
элементов — допустимые данные, а не недоступная запись пользовательского среза. Неудача проверки
не выдаётся за установленное отставание. Готовая часть, не охватывающая
предъявленные изменения, не выдаётся за успешный ответ; внутреннее чтение
и кэширование такой части допустимы. Общее подтверждение может использоваться
для связанных чтений одной ревизии; обязательная дорогая проверка каждой
части отдельно не вводится.

## Одна точка настройки доступа

При подключении составного интерфейса использующий код предоставляет одну
согласованную конфигурацию доступа. Она объединяет возможности для DAG
и выдачи и гарантии, необходимые координатору. Каждый модуль зависит
только от своей логической части контракта. DAG-модуль не получает
обязанности управлять страницами, а модуль выдачи — вычислять переходы.

Реализация доступа может использовать несколько внутренних адаптеров.
Их совместимость и выполнение общих гарантий обеспечивает реализация
этого доступа, а не обработчик каждого действия пользователя.
Одна точка настройки не означает один класс, пакет, endpoint, backend
или серверную сессию. Конкретный формат конфигурации здесь не задаётся.

Принята одна точка настройки: согласованная конфигурация подключается
как целое, логические обязанности остаются разделёнными. Компромисс —
произвольные реализации источников нельзя считать совместимыми без
адаптации и общей гарантии данных. Возможность использовать несколько
внутренних адаптеров сохраняется, отдельный публичный ручной протокол
сборки частей не возвращается.

## Границы и оставшиеся решения

Логические имена, аргументы и ответы четырёх предметных операций приняты
и сведены выше. Это не утверждает ещё открытые поля общей выдачи или
физическое представление доступа.

Остаются физические типы и оболочки аргументов/ответов, способ передачи
ревизии и контекста изменений, параметры выдачи, жизненный цикл и
восстановление. Смысл условий чтения уже принят и не пересогласуется.
[Граница прекращения ненужной работы принята](coherent-result-contract.DRAFT.md#прекращение-ненужного-получения);
точный способ сообщения и ограничения ресурсов ещё открыты. Механизм ожидания
и физическая форма асинхронного ответа
не выбраны. Имена
проверяются по [правилу терминологии контрактов](../../../AGENTS.md#contract-terminology).

Серверный сеанс, привязка к экземпляру backend, обязательное хранение всех
ревизий и загрузка всех элементов на устройство не вводятся. Полнота
переходов и точность количеств сохраняют ранее принятые требования;
одна точка подключения сама по себе не уменьшает их стоимость.
Эффективность восстановления места чтения и сквозного пути ещё не доказана.
Новых замеров, реализации, SLA или решения OpenAPI этот шаг не содержит.
