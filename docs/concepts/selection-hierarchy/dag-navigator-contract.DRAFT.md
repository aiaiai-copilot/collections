## 1. Ответственность

**Порядок согласования уточнён 2026-09-14:** сначала самостоятельность модуля,
затем актуальность и порядок обновления данных, после этого устойчивость
пользовательского выбора при обновлении. Пользователь согласовал этот порядок,
а следующим ответом «Да» подтвердил базовую самостоятельность ниже.

**Принятая граница ответственности, зафиксирована 2026-09-19:**

- Навигатор управляет выбранными тегами, режимом, фактической историей
  и своим отображением.
- Приложение отвечает за получение и сохранение данных и показ результатов.
- Взаимодействие идёт через явный интерфейс. Навигатор не привязан
  к конкретному серверу, базе или глобальному состоянию приложения.

Такая самостоятельность позволяет отдельно проверять и переиспользовать
навигатор, но не означает замороженные данные. Изоляция лаборатории остаётся
способом проверки, а не готовой политикой актуальности целевой системы.
Автоматическая передача обновлений от приложения принята ниже. Формат обмена,
согласованность обновлений и место вычисления направлений ещё предстоит
определить. Приведённая ниже детализация соответствует прототипу; базовая
граница принята, но все технические детали её реализации этим не утверждены.

Навигатор меняет **текущий набор навигации**, но не редактирует фильтры
подборок и теги элементов. Приложение показывает результаты этого набора.

| Владелец | Ответственность | Не входит |
| --- | --- | --- |
| Модуль навигации | Текущий набор и его разрешение в узел, режим, фактическая история; родители, направления и подсказки; локальное отображение облака | Создание/изменение подборок и элементов, сохранение данных, маршрутизация приложения |
| Хост результатов | Список элементов, его сортировка и страницы; название выборки со счётчиком; открытие, закрытие и перетаскивание панели | Собственная конкурирующая история навигатора, вывод родителей из фактического маршрута |
| Источник данных приложения | Согласованные сведения о подборках и элементах одного личного пространства | Решение за пользователя, какой набор выбрать |

Выпадающий выбор `Узлы / Свободно` рисует хост, но значение режима принадлежит
навигатору. Хост передаёт команду и отображает полученное состояние.
Идентичный фильтр должен давать одинаковый состав в обоих режимах.

## 2. Данные на входе

**Принято 2026-09-19: автоматическое поступление обновлений.** Когда
приложение узнаёт об изменениях подборок или элементов, оно автоматически
передаёт обновлённые данные навигатору через согласованный интерфейс.
Отдельное нажатие «Обновить» для этого не требуется. Сам навигатор сервер
не опрашивает.

Это правило целевого взаимодействия, ещё не реализованное в статическом
прототипе. Оно не предрешает сетевой механизм приложения, точную задержку,
согласование версий. Сохранение текущих выбранных тегов согласовано отдельно
в разделе 3, возврат по истории после обновления — в разделе 4.
Автоматическое поступление и реакция текущей выборки — разные решения.
Ожидание фонового обновления при неизменных тегах и согласованная замена
отображаемых данных приняты в разделе 7; конкретный протокол этого обмена
ещё не выбран.

Для вычисления поведения нужны:

- Пользовательские узлы: непрозрачный `id`, имя, нормализованный AND-набор тегов.
- Сведения о принадлежности элементов тегам: достаточно идентичности элемента
  и тегов, содержимое карточек навигатору не нужно.
- Начальное положение и режим; восстановленная история — только если её
  явно передал владелец сеанса. Размер контейнера задаётся окружением.

**Факт реализации:** `fixture.nodes` и `fixture.items` полностью передаются
при создании. Данные копируются; замены данных во время сеанса нет.
Это допустимый профиль автономного эксперимента, а не требование загружать
в браузер все реальные элементы. Протокол получения счётчиков, направлений
и подсказок на больших данных здесь пока не выбирается.

**Предложение для входных гарантий:** один снимок одного личного пространства;
уникальные ID; не более одного пользовательского узла на нормализованный
фильтр; согласованные теги каждого элемента. Противоречивые дубликаты не
разрешать правилом «кто встретился первым». Неправильный снимок или неизвестный
начальный ID должны давать явную ошибку инициализации, а не молчаливый переход
в «Всё». В прототипе полной валидации пока нет.

Нормализация прототипа: обрезка краёв строки, приведение к нижнему регистру
`ru`, удаление пустых значений и повторов, сортировка `ru`. Для сравнения
важен набор, не порядок ввода. Это не утверждает синонимы, стемминг или
эквивалентность `е/ё`. Продуктовое правило идентичности тегов должно быть
единым с источником данных; точный Unicode/locale-профиль ещё не утверждён.

**Найденное ограничение:** core нормализует свою копию данных, а хост
фильтрует исходные теги элементов. Текущие фикстуры заранее нормализованы,
но произвольный внешний снимок может дать разные счётчики. Будущему интерфейсу
нужен единый нормализованный источник, а не две расходящиеся трактовки тегов.

## 3. Состояние и идентичность

Подтверждены три положения:

```ts
type Location =
  | { kind: 'all'; tags: []; nodeId: null }
  | { kind: 'node'; tags: string[]; nodeId: string }
  | { kind: 'temporary'; tags: string[]; nodeId: null };

type Mode = 'nodes' | 'free';
type RouteEntry = { location: Location; mode: Mode };
```

Это описание смысла, не буквальная схема wire-объектов прототипа:
его история плоская (`kind`, `tags`, `nodeId`, `mode`).

- `all` — явное «Всё», не пользовательская подборка.
- `node` — существующая подборка, чей фильтр совпадает с текущим набором.
- `temporary` — непустой набор без совпадающей подборки. Слово осталось техническим
  обозначением промежуточного узла, а не названием на экране.
- Точный непустой набор разрешается в `node`, если такая подборка существует,
  иначе в `temporary`. Определяющим является набор, не название.
- Пустой набор после снятия последнего тега даёт именно `all`. Сохранённая
  подборка с пустым фильтром открывается отдельным явным переходом из `all`
  по её ID в обоих режимах. Доступ в `free` принят 2026-09-19, но пока
  не реализован в прототипе.
- Поэтому одного массива тегов недостаточно для идентификации положения:
  `all` и сохранённый пустой фильтр дают одинаковые элементы, но разные узлы.

Имя и число релевантных элементов — производные. Имя сохранённого узла
показывается как `Фильмы (6)`, общего набора — `Всё (12)`; у промежуточного
используется выражение тегов. Навигация не создаёт и не сохраняет такое имя.

**Принято 2026-09-19: устойчивость текущего набора при обновлении.** Изменение
фильтра открытой подборки или её удаление не меняет уже выбранные теги.
Результаты пересчитываются по этому набору на свежих данных; сохранение
фильтра не означает сохранение старого списка элементов или счётчика.
Соответствие набора пользовательской подборке определяется заново. Если
для непустого набора совпадения больше нет, положение становится промежуточным.

Например, при выборе `фильм + спокойное` удаление `спокойное` из определения
открытой подборки не переключает текущую выборку на все фильмы. Удаление
самой подборки также не сбрасывает выбранный набор в «Всё».
Это принятое правило целевого интерфейса, не реализованное пока в прототипе.
Восстановление старых записей истории согласовано отдельно в разделе 4.

**Принято 2026-09-19: исчезновение пустой именованной подборки.** Если открытая
подборка с пустым фильтром удалена или её фильтр стал непустым, выбранные теги
остаются `[]`, а положение становится `all` («Всё»). Отдельный пустой
промежуточный срез не создаётся; обновление данных не добавляет шаг истории.
Если выбранная подборка по-прежнему существует с пустым фильтром, она остаётся
именованным узлом, отличным от `all`. Само `all` не превращается в неё
автоматически. Это правило целевого поведения, ещё не реализованное
в статическом прототипе.

Для хоста полезны два разных сравнения:

- **Положение:** `kind + nodeId + нормализованные tags`; изменение может
  требовать обновить имя и действия, даже если состав не изменился.
- **Запрос состава:** нормализованные теги в одном пространстве и одном
  снимке данных. Режим, история, размер облака и открытость панели не входят.
  При изменении самих данных одних тегов для кэширования недостаточно.

## 4. Подтверждённые переходы

| Действие | Положение и режим | История | Результаты |
| --- | --- | --- | --- |
| Направление вниз, `nodes` | Ближайший пользовательский узел с большим набором тегов; добавляется весь показанный набор одного назначения | Предыдущее положение и режим добавляются | Применяется новый AND-набор |
| Направление вниз, `free` | Добавляется один тег; точное совпадение может дать пользовательский узел | То же | То же |
| Родительская кнопка | Переход в ближайшую более широкую пользовательскую подборку | То же | Применяется её набор |
| Снятие выбранного тега | Доступно в обоих режимах, включая последний тег; режим не меняется | То же | Применяется оставшийся набор |
| Ручное добавление | Только `free`; весь введённый пакет добавляется атомарно | Одна запись на пакет | Обновляются после применения, не при наборе |
| Смена режима | Положение не меняется | Не добавляется и не очищается | Состав и страница сохраняются |
| «Назад» | Восстанавливаются прежние теги и режим; соответствующая подборка определяется по актуальным данным | Последняя запись снимается; текущая не добавляется | Актуальные элементы для восстановленного набора |
| «Всё» | Явный `all` в текущем режиме | Предыдущее положение сохраняется | Все элементы |

**Принято 2026-09-19: возврат после обновления данных.** «Назад» восстанавливает
теги и режим предыдущего фактического перехода, но не старую версию данных.
Совпадающая подборка, её имя и результаты определяются по актуальным данным.
Если прежняя подборка изменилась или удалена, запись не пропускается и её
теги не заменяются новым фильтром старого ID. Непустой набор без совпадения
открывается как промежуточный срез. Само обновление данных не добавляет шаг
истории, даже если меняет идентичность текущего положения.

История — маршрут выбора, не архив состава элементов. Прежняя страница
результатов, черновик и прокрутка этим решением не восстанавливаются.
**Принято 2026-09-19:** при возврате к бывшей пустой именованной подборке,
которая удалена или теперь имеет непустой фильтр, восстанавливаются пустые
теги и прежний режим, а положение — `all`. Запись не пропускается,
даже если восстановленное положение совпало с текущим. Отдельный пустой
промежуточный срез не создаётся.
Правило обновлений пока не реализовано в статической фикстуре:
там `back` восстанавливает записанный `nodeId` без повторного разрешения.

Исключение к строгому добавлению тегов: явный переход из `all` в сохранённую
подборку с пустым фильтром меняет положение без добавления тегов.
**Принято 2026-09-19:** этот переход доступен и в `nodes`, и в `free`.
Меняются идентичность и имя положения, но не запрос состава результатов;
предыдущее положение и режим сохраняются в истории как при обычном переходе.
Наличие пустой подборки не означает автоматического входа в неё из `all`.
Конкретное визуальное оформление перехода ещё не выбрано.

Родители выводятся из включения фильтров, а не из истории. При нескольких
родителях показываются все ближайшие; выбор первого за пользователя запрещён.
В `free` родительская колонка скрыта. Смена режима не переносит промежуточный
набор в ближайшую подборку. Кнопка «Назад» без истории недоступна.

**Факт реализации:** успешный переход, возврат и смена режима очищают
черновик ввода и локальную ошибку. Само открытие/закрытие панели сохраняет
черновик. История хранит положение и режим, но не прежний черновик, страницу
результатов или положение прокрутки. Не обещаем восстановления всего экрана.
«Назад» восстанавливает режим, сохранённый при уходе из прежнего места,
а не отменяет последнюю смену режима как отдельное действие.

Масштаб не меняется автоматически; размеры могут подстроиться для доступности
направлений. Это отображение, а не дополнительный навигационный переход.
Переход и смена режима перерисовывают облако и выбранные теги с начала;
масштабирование/resize при сохранении прокрутки удерживают её относительную
позицию. История не является архивом этих параметров отображения.

## 5. Результаты, направления и ввод

Число результатов — число **уникальных ID элементов**, содержащих каждый тег
набора. Оно не равно сумме счётчиков дочерних узлов. Пустой результат допустим
и не означает ошибку навигации. Неизвестный введённый тег допустим; он не
создаёт запись в словаре и не создаёт подборку.

В `nodes` направления — ближайшие пользовательские строгие надмножества,
а из `all` — корни. Многотеговая кнопка добавляет теги **одного назначения**,
не все теги облака. В `free` доступны известные однотеговые уточнения из
подходящих элементов и пользовательских потомков. Режим не перечисляет
все математически возможные промежуточные наборы.
Отдельное принятое исключение — явный переход из `all` в существующую
пустую именованную подборку в обоих режимах; он не заменяет обычные
однотеговые уточнения `free` и не должен делать их недоступными.

Нулевой счётчик не убирает пользовательский узел из навигации. Все
пользовательские назначения должны оставаться достижимыми: для каждого
потомка есть сохраняемый первый шаг, являющийся подмножеством его фильтра.
Доступное через прокрутку не равно видимому сейчас. Масштаб и тесный контейнер
не должны незаметно исключать назначения; предельная недоступность сообщается.

**Факт реализации, не целевая норма:** сейчас из `all` в режиме `free`
наличие пустой именованной подборки даёт `unrepresentable` и блокирует
всё облако, не только переход в неё. Произвольное другое положение в `free`
её наличие не блокирует. Принятое правило явного доступа требует изменения
этого поведения; в текущем шаге код не меняется.

Ручной ввод: пробел разделяет теги, `_` остаётся частью тега. Enter или `+`
применяет пакет. Пустой ввод и пакет уже выбранных тегов не добавляют историю
и не порождают навигацию; показывается локальное сообщение.

Подсказки используют выбранные теги и завершённые слова черновика как AND-
контекст; последний фрагмент ищется в названии тега без учёта регистра.
Выбранные/завершённые теги исключаются. Только подсказки с положительным
счётчиком предлагаются, по убыванию числа, затем по названию. Число в
`спокойное (5)` — оформление подсказки, не часть добавляемого тега.

## 6. Что существует сейчас и что предлагается публично

### Фактический интерфейс

`createDagNavigator(element, options)`:

- Вход: `fixture`, `initialState`, `onStateChange`, `onEvent`.
- Возвращает `getState()`, `setMode(mode)`, `refreshLayout()`, `destroy()`.
- `getState`/`onStateChange` отдают большой отладочный снимок: положение,
  историю, подсказки, родителей, направления, счётчик, пиксели и покрытие облака.
- Первый `onStateChange` синхронно приходит внутри создания модуля, до возврата
  handle. Далее он вызывается при действиях, вводе и перерасчётах layout.
  Его вызов **не означает**, что изменились теги.
- В навигационном действии новая отрисовка и `onStateChange` предшествуют
  `onEvent({type, payload, before, after})`. Позднее могут прийти дополнительные
  снимки layout. `requestResults` вызывает только `onEvent`, без смены состояния.
- Scroll облака сообщает снимок; scroll выбранных тегов меняет только DOM-
  подсказки. Не следует строить приложение на частоте диагностических вызовов.
- `setMode` игнорирует неизвестное/уже активное значение; внешний вызов не
  переводит фокус внутрь модуля. Скрытие панели не вызывает `destroy`.

Снимок не является готовым форматом восстановления: `initialState` не
восстанавливает черновик, scroll и вычисленное покрытие. Некоторые объекты
диагностики отдаются по внутренним ссылкам — это не immutable-протокол.

### Предлагаемый интерфейс

Сохранить четыре существующих способа управления: чтение состояния,
смену режима, обновление layout и уничтожение. Публичный `getState()` должен
возвращать небольшой `NavigationState`, а диагностика — отдельный отладочный
снимок. Это предложение по разделению интерфейса, **не** уже сделанный рефакторинг.

```ts
type NavigationState = {
  location: Location;
  mode: Mode;
  canGoBack: boolean;
  relevantCount: number | null; // null — число для выбранного набора ещё неизвестно
  selectionName: string; // имя либо выражение тегов, не новая подборка
};

// Предлагаемые уведомления, ещё не реализованы:
onNavigationState(state: NavigationState): void;
onSelectionChange(change: {
  reason: 'initialize' | 'refine' | 'broaden' | 'filterInput' | 'back' | 'all' | 'dataUpdate';
  previous: Location | null;
  current: Location;
  state: NavigationState;
}): void;
```

`onNavigationState` сообщает изменившееся публичное состояние, включая режим,
и начальное состояние. `onSelectionChange` вызывается один раз на изменение
положения и один раз для начального положения. Первичное уведомление не
создаёт запись истории. Новое публичное состояние сообщается до уведомления
об изменении выборки. Получатель использует переданные значения и не должен
вызывать ещё не возвращённый handle во время инициализации.

В проекте `relevantCount` допускает `null`, чтобы согласованное ожидание
новой выборки не кодировалось ложным нулём. Это уточнение предлагаемой схемы,
не изменение прототипа; полный формат состояний загрузки и ошибки ещё
предстоит определить.

При неизменном положении ввод, layout, прокрутка и смена режима не вызывают
`onSelectionChange`. Выбор пустой именованной подборки из `all` вызывает его,
хотя теги одинаковы: хост меняет имя, но не обязан заново загружать тот же
состав или сбрасывать страницу. Сравнение тегов остаётся отдельным правилом
хоста; событие изменения положения не тождественно сетевому запросу.

В проекте интерфейса предложена причина `dataUpdate` для изменения
идентичности положения после обновления данных при прежних тегах — например,
из пользовательского узла в промежуточный. Это не реализованное событие
прототипа. Если обновились только элементы, идентичность и даже число могут
не измениться: хост всё равно обновляет список по новым данным приложения,
не ожидая обязательного `onSelectionChange` или изменения счётчика.

Публичные снимки должны быть отделёнными значениями без ссылок, позволяющих
изменять внутреннее состояние модуля. Полная история, подсказки, размеры и
причины ограничения остаются в диагностике. Они не являются командами
загрузки результатов. Новые команды открытия по внешней ссылке, замены данных
и восстановления сеанса не объявляются до решений из раздела 8.

Аудитные причины `refine`, `broaden`, `filterInput`, `modeChange`, `back`,
`all`, `scaleChange`, `cloudResize` сохраняют различие действий. Их текущие
payload описаны в минимальном контракте; приложению не нужно обрабатывать
их все для показа списка. `requestResults` остаётся необязательным намерением
контрольной лаборатории, **не** условием обновления постоянной панели.

### Существенные детали текущих событий

- `refine`: `{addedTags, nodeId}`, в том числе законный `addedTags: []` для
  явного перехода из `all` в пустой сохранённый узел.
- `broaden`: у родителя `{removedTags, nodeId}`, у снятия тега
  `{removedTag, removedTags: [removedTag]}`. Итоговый ID берётся из `after`.
- `filterInput`: `{addedTags}`, не исходная строка; `all`: `{}`.
- `back`: `{from, restored}` с описаниями положений; режим находится в `after.mode`.
- `modeChange`: `{from, to}`; `requestResults`: `{tags, nodeId, relevantCount}`.
- `scaleChange`: `{from, requested, to, limited}`; `cloudResize` — те же поля
  для `{width, height}`, при pointer-жесте ещё `cancelled`.
  `requested` уже ограничен допустимым диапазоном, не обязательно равен сырому
  запросу. Pointercancel сообщает возврат к начальному размеру; жест без
  движения не создаёт события resize. Это диагностические детали, не новые
  требования к пользовательскому интерфейсу.

## 7. Правила хоста результатов

Подтверждено в отдельном эксперименте:

- Применённые теги меняются — в статическом эксперименте список обновляется
  сразу и начинается с первого результата. Повторного «Показать результаты»
  не требуется; целевое ожидание внешних данных согласовано ниже.
- Смена режима, ввод черновика, масштабирование и открытие/закрытие панели
  не меняют состав и текущую страницу.
- Панель накрывает часть результатов; её открытие не уменьшает расчётную
  площадь списка и не меняет разбиение на страницы.
- При изменении размера окна адаптивное разбиение сохраняет прежний первый
  видимый элемент на текущей странице; при нуле элементов страниц нет.
- Название, счётчик в заголовке и фактический список относятся к одному набору
  и снимку данных. Не показывать старый счётчик как число для нового набора.

**Принято 2026-09-19: ожидание фонового обновления.** Если выбранные теги
не менялись, до готовности обновления остаются видимыми предыдущий список
и навигация с ненавязчивым индикатором ожидания. После получения согласованных
новых данных вместе обновляются направления, счётчики и видимая страница
результатов. Новый счётчик не показывается со старым списком; частично
полученные сведения не подменяют отдельные части прежнего согласованного
экрана.

Это правило целевого поведения, а не результат проверки статического
прототипа: ожидание внешних данных в нём ещё не реализовано. Согласованность
видимой страницы не требует заранее загрузить все страницы результатов.
Оформление индикатора, механизм согласования версий, сохранение позиции
при изменении состава этим решением не определены. Ошибка фонового
обновления и ожидание после выбора другого набора согласованы отдельно ниже.
Правило ожидания относится к фоновому обновлению
той же выборки, а не разрешает выдавать прежний список за результаты новых
выбранных тегов.

**Принято 2026-09-19: ошибка фонового обновления.** Если обновление той же
выборки завершилось ошибкой, сохраняются последний согласованный экран,
выбранные теги и история. Индикатор ожидания заменяется коротким сообщением
«Не удалось обновить» с действием «Повторить». Ошибка не превращается
в нулевой результат и не сбрасывает выбор в «Всё».

«Повторить» — способ восстановления после ошибки, а не обязательный шаг
обычного автоматического обновления. Сам повтор не является навигационным
переходом. Это принятое целевое поведение, пока не реализованное в прототипе;
стратегия автоматических повторов, ошибка первоначальной загрузки и ошибка
загрузки после выбора другого набора этим решением не определены.

**Принято 2026-09-19: ожидание после смены выбранных тегов.** Новый выбранный
набор показывается сразу. Если данные для него ещё загружаются, прежние
результаты и направления заменяются состоянием загрузки. Неизвестное число
результатов не показывается ни как ноль, ни как счётчик прежней выборки.
Когда согласованные данные готовы, вместе показываются новый список,
счётчики и направления; результаты нового набора начинаются с первой страницы.

Это отличается от фонового обновления прежнего набора: старый список
не остаётся под новыми тегами. Правило не требует искусственного ожидания,
если нужные согласованные данные уже доступны. Конкретное оформление
загрузки, её ошибка и обработка запоздалых ответов ещё не согласованы;
в статическом прототипе ожидание не реализовано.

Измерение всех синтетических строк в DOM — реализация эксперимента,
не требование к загрузке больших списков. Пагинация и загрузка строк остаются
у хоста, вне интерфейса навигатора. Его `panelChange`, `pageChange` и
`panelDragReturn` — записи собственного журнала, не события core-навигации.

## 8. Не закрыто приёмкой прототипа

1. **Протокол и согласованность обновлений.** Автоматическая передача
   известных приложению изменений, ожидание и ошибка фонового обновления,
   а также ожидание после смены выбранных тегов приняты. Ещё уточняются
   формат обмена, источник вычисления направлений, подсказок и счётчиков,
   механизм согласования версий, ошибки первоначальной загрузки и нового набора,
   автоматические повторы, устаревшие ответы и сохранение позиции в списке
   при изменении состава.
   Ни полный клиентский индекс, ни сетевой протокол пока не утверждены.
2. **Восстановление сеанса.** Канонический ID подборки определён словарём,
   но URL промежуточного набора, браузерный Back, обновление страницы и
   долговременное хранение режима/маршрута в этом эксперименте не реализованы.
   Параметры `scenario/mode` — не контракт пользовательских ссылок.

Финальная шкала веса направлений, обучающие пояснения и дополнительные
мобильные условия остаются отдельными вопросами карты. Они не оправдывают
повторную полировку принятой компоновки перед обсуждением контракта.

## 9. Будущая проверка интерфейса

При реализации проверять через публичный интерфейс, а не внутреннюю разметку:

- Несколько родителей: переход вверх и «Назад» ведут в разные состояния.
- `nodes` + промежуточный набор: режим сохраняется, одиночный тег снимается.
- Последний тег → `all` → «Назад» восстанавливает набор и прежний режим.
- Изменение/удаление подборки после ухода из неё не удаляет шаг истории:
  «Назад» восстанавливает прежние теги и режим с актуальными результатами.
  Автообновление данных само не создаёт шагов возврата.
- Ручной пакет → одно изменение выборки; черновик и дубликаты → ни одного.
- Обновление/удаление открытой подборки сохраняет теги, а результаты
  пересчитываются по свежим данным; непустой набор без совпадения становится
  промежуточным. Изменение состава с прежним счётчиком тоже отражается в списке.
- Переход `all` ↔ пустая именованная подборка в обоих режимах меняет
  идентичность, не состав. В `free` при этом остаются доступны обычные
  однотеговые уточнения; наличие пустой подборки не блокирует облако.
- Удаление выбранной пустой подборки или изменение её фильтра на непустой
  сохраняет `[]` и даёт `all`, без нового шага истории. При «Назад» к такой
  подборке восстанавливаются `all` и прежний режим; запись не пропускается,
  даже если положение совпало с текущим. Пустой `temporary` не появляется.
- Пока выбранная пустая подборка существует с пустым фильтром, она остаётся
  именованным узлом; обновление данных само не объединяет её с `all`.
- При задержке фонового обновления неизменной выборки прежний список
  и навигация остаются видимыми с индикатором ожидания. Частично пришедшие
  данные не создают смешанный экран; готовое согласованное обновление меняет
  направления, счётчики и видимую страницу результатов вместе.
- При ошибке фонового обновления прежний согласованный экран, теги и история
  сохраняются; ожидание сменяется сообщением «Не удалось обновить» и действием
  «Повторить». Ошибка не даёт ложного нуля или сброса в `all`; повтор
  не создаёт шага истории и не становится обязательным для обычных обновлений.
- Если после смены тегов новые данные ещё не готовы, выбранный набор виден
  сразу, а прежние список и направления заменены загрузкой. Неизвестный
  счётчик не подменяется нулём или старым числом. Готовые согласованные
  список, счётчики и направления появляются вместе, список — с первой страницы.
- Общий элемент нескольких подборок считается один раз, нулевой узел достижим.
- Смена режима на странице 2 не сбрасывает страницу; новый набор сбрасывает.
- Прокрутка и resize не вызывают загрузку состава; покрытие остаётся честным.
- Неверный вход не создаёт ложное состояние, внешняя правка снимка не меняет
  внутренний сеанс, уничтожение освобождает подписки и не создаёт событий.

Это критерии будущей реализации, не отчёт о новых автотестах. В данном шаге
проверяется документация по исходникам; приложение, backend и UI не меняются.
