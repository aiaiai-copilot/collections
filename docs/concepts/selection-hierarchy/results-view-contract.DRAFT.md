# Общий контракт выдачи результатов

Родитель: [Навигация и получение результатов](../../product/navigation-and-results.md).
Связь: общий механизм — определяет просмотр выдачи независимо от DAG.

Этот проект описывает работу с упорядоченной выдачей: страницы, размер,
порядок, место чтения, ожидание получения и ошибки. Выборку задаёт
вызывающее приложение; правила выбора могут принадлежать DAG-навигатору,
поиску или другому способу навигации.

Документ определяет требования к выдаче результатов и открытые вопросы интеграции.

## Готовая основа и отличия приложения

Для общего просмотра выбирается готовое решение, его совместимость
с требованиями приложения проверяется один раз, а отдельно обсуждаются
лишь реальные отличия. Обычные функции и значения выбранной основы
заимствуются, а не проектируются заново по полям.

[Сопоставлены готовые варианты](../../research/results-view-reuse-options.md):
TanStack Table v8 для нумерованных страниц и Relay Connections как иной,
курсорный подход. Модель TanStack принята ниже; библиотечная зависимость,
обязательная пагинация для любого источника, язык и сетевой протокол не выбраны.

Сохраняются уже принятые требования, включая согласованность списка,
счётчиков и навигации, различение пустой выдачи и ошибки и сохранение места
чтения по элементу. Готовая основа не отменяет их и не доказывает стоимость
получения страниц или восстановления позиции на конкретном источнике.

[покрытие и интеграция](../../research/results-view-reuse-options.md#совместимость-tanstack-v8-с-принятыми-правилами-приложения).
TanStack Table v8 покрывает обычный механизм нумерованных страниц;
сохранение места по ID и согласованная подготовка всего результата
остаются внешними по отношению к нему. Вывод о совместимости документальный,
без проверки выполнения или производительности. Использовать эту модель
как ограниченную основу принято отдельным решением ниже.

## Принятая основа нумерованного просмотра

Основа — модель пагинации [TanStack Table v8](https://tanstack.com/table/v8/docs/guide/pagination):
обычные переходы, изменение размера страницы и управляемое состояние.
Типовые детали берутся из неё; новый универсальный механизм не проектируется.
Фиксируется версия модели v8, не установленная версия пакета или привязка
к конкретному UI-фреймворку. Принятие не требует табличного вида результатов.

Ниже сведена интеграция с уже принятыми требованиями, а не новые политики:

| Часть | Обязанность в текущем применении |
| --- | --- |
| Механизм страниц на принятой основе | Обычные переходы, размер и состояние страниц; работа с подготовленной упорядоченной страницей |
| Общая выдача и настроенный доступ | Получить нужную область; при обновлении восстановить место по ID и принятым запасным ориентирам; отличить новый фильтр от обновления прежнего |
| Общая координация результата | Проверить полноту, совместимость и актуальность частей; применить страницу, количества и DAG согласованно; сохранить принятые правила ожидания и ошибок |
| Отображение | Рассчитать адаптивный размер по доступной площади и передать его механизму страниц |

Обычный сброс индекса или сохранение номера страницы не подменяют поиск
по ID при обновлении. Передача страницы библиотеке сама по себе не
доказывает её совместимость со счётчиками и навигацией. Эти требования
обеспечиваются интеграцией, а не переписыванием алгоритма пагинации.

Точные формы обращения к источнику и проекция состояния основы в составной
результат относятся к дальнейшей интеграции.
Обычные понятия и операции следуют принятой основе.
Смысл `view` как параметров фактически полученных данных сохраняется.

Подключение библиотеки или копирование кода не выполняется. Номера страниц
не становятся обязательными для каждого источника; курсорная модель не
принимается этим решением. Прямой доступ к далёкой странице, последней
странице и месту по ID требует подходящих возможностей источника.
Пригодность модели интерфейса не является гарантией стоимости этих операций.

## Область ответственности

Выдача получает заданную выборку и параметры её представления, обеспечивает
получение нужной страницы и сообщает фактически доступные данные и ход
обновления. Способ указания выборки, интерфейс источника, типы и реализация
ещё предстоят. Понятия родителей DAG и режима навигации принадлежат
вызывающему модулю.

Связи для текущего приложения описаны в
[верхнеуровневом интерфейсе](dag-navigator-upper-interface.DRAFT.md#связи-навигации-и-выдачи).
Он согласует выдачу с вариантами навигации и количествами в целостном
комплекте. Теги, режим и навигационная история управляются через тот интерфейс.
Общий механизм маршрута выделен в [контракт истории посещений](navigation-history-contract.DRAFT.md);
страницы выдачи сами по себе не становятся посещениями этого маршрута.

## Элементы и вхождения

Единица выдачи определяется исходной областью представления.
В теговом пространстве и коллекции каждый подходящий элемент представлен
один раз. В подборке выдача содержит все вхождения подходящих элементов
по [прикладным правилам представления](../../product/product-design.md#представления).
Срез уникальных элементов и список вхождений различаются.

Ниже правила получения страницы и сохранения места применяются
к единицам выдачи. Для списка уникальных элементов единица определяется
ID элемента. Для подборки нужно различать вхождения одного элемента:
его ID не позволяет отличить первое присутствие от повторного.

Счётчики DAG относятся к уникальным элементам целевого среза.
Их нельзя использовать как количество строк или основание расчёта
страниц подборки. Форма передачи идентичности вхождений и согласование
количеств выдачи со счётчиками DAG требуют формализации.
Отдельное поле или новый способ пагинации этим не вводится.

## Уже принятые правила текущего приложения

Сохранение места по элементу при фоновом обновлении, подтверждённая пустая
выдача, различение ожидания и ошибки, согласованное применение данных
приняты ранее в
[основном контракте](dag-navigator-contract.DRAFT.md#7-правила-хоста-результатов).
В этом проекте они служат исходными требованиями текущего применения.
Для других приложений состав обязательных правил общего контракта
потребует отдельного определения. Стоимость восстановления места
остаётся открытой; основа нумерованного просмотра принята выше.

## Получение страницы без отдельного поиска позиции

Это интерфейс доступа для общей выдачи, не пятая операция DAG и не новый механизм пагинации.
Использующему коду приложения поиск позиции не передаётся.

Принято одно логическое получение готовой страницы с двумя способами
указать требуемое место:

| Задача | Что задаётся по смыслу | Что должно быть получено |
| --- | --- | --- |
| Обычный переход | Выборка, порядок, размер и выбранная страница по принятой модели | Упорядоченные элементы этой страницы и сведения о фактически полученной странице |
| Фоновое обновление с сохранением места | Та же выборка и порядок, размер, ID прежнего первого видимого элемента и достаточные сведения для восстановления | Страница с сохранённым ориентиром либо с запасным ориентиром по принятому правилу |

При пустой выдаче результат не содержит страницы; это не ошибка получения.
Требование доступности данных для отображения элементов сохраняется.
Условия чтения и связь с ревизией берутся из
[общего доступа](dag-navigator-data-access.DRAFT.md#логический-состав-обращения),
не вводятся повторно. Количество можно получить или переиспользовать
в составе согласованной сборки; повторный подсчёт и второе публичное поле
количества не требуются.

Разделение на «найти позицию» и «получить страницу» может существовать
в реализации доступа, но отдельный обязательный метод поиска позиции
потребителю не требуется. Так ему не нужно согласовывать промежуточную
позицию с последующим чтением страницы. Альтернатива — два метода — имеет
смысл, если найденная позиция нужна независимо от получения страницы;
в текущих требованиях такой потребности не установлено.

Это не обещание одного сетевого запроса, отдельного backend, серверной сессии
или одинаковой стоимости для всех источников. Имя операции, машинные поля
и способ передачи сведений для восстановления пока не выбираются. Готовность
этой части не заменяет согласованного применения всего комплекта.

### Достаточность сведений для восстановления

Принятый запасной ориентир ищется среди элементов всего прежнего списка
в прежнем порядке, а не только среди элементов показанной страницы. Например, прежняя страница
содержала A и B, а следующая начиналась с C. Если A и B исчезли, но C остался,
правило требует найти C. Данные только новой выдачи и ID A в общем случае
не устанавливают, что C был следующим подходящим элементом прежнего списка.

Нужны сведения о прежнем составе и порядке, достаточные для такой проверки.
ID существующего элемента позволяет различать элементы, но сам по себе
не описывает прежних соседей. Новые элементы нельзя автоматически принимать
за запасной ориентир только потому, что они находятся рядом в новой выдаче.

Обязательный архив всех списков, полная выгрузка в браузер, срок хранения
прежних сведений и конкретный способ поиска не приняты. Из требования
восстановления не следует единственный способ хранения. Однако поддержка
точного правила конкретным источником пока не доказана: до выбора реализации
нужно проверить достаточность доступных сведений и стоимость их получения.
Нельзя молча ограничить поиск показанной страницей, заменить его сохранением
номера страницы или выдать невозможность восстановления за пустую выборку.
Политика на случай недоступности необходимых прежних сведений остаётся
открытым вопросом интеграции, не новым автоматически принятым отказом.

## Данные элемента выдачи

Данные единицы выдачи должны обеспечивать отображение по требованиям
приложения; обязательное копирование исходного элемента в каждый результат
не требуется. Идентичность элемента и идентичность его вхождения
различаются согласно [исходной области выдачи](#элементы-и-вхождения).

`items` — элементы полученной страницы в согласованном порядке, а не весь
выбранный набор. Готовый результат обеспечивает доступность данных,
необходимых для согласованного представления элементов в списке, без
отдельной догрузки этих данных приложением. Готовность списка не означает
обязательную готовность полного содержимого каждого элемента для всех
последующих действий. Состав данных для отображения определяется требованиями
конкретного приложения; универсальные поля названия, аннотации или тегов
здесь не вводятся.

Например, для списка документов могут быть нужны названия и теги, но не
полный текст. Такой список может быть готов до получения текста для
последующего открытия документа. Если же согласованное представление
списка включает фрагмент текста, готовность распространяется и на него.
Это пример достаточности данных, не утверждение формы карточки или
контракта открытия/редактирования элемента.

Для сохранения места чтения в списке уникальных элементов используется
существующий ID элемента. В подборке требуется идентичность вхождения.
Это применение принятой модели и правила сохранения места, не новое
условие сходства содержимого. Изменение содержимого того же элемента
не меняет его идентичность; при выходе из выборки действует принятое
правило следующего/предыдущего сохранившегося элемента. Технический тип
ID и расположение его поля сейчас не выбираются. Поддержка источников
без устойчивой идентичности не добавляется как новый вопрос этого контракта.

**Принято:** доступность не требует копирования данных в каждый результат.
Действуют общие условия согласованности и неизменяемости готового комплекта.
Физическая упаковка открыта; обязательная структура `{ id, data }` не вводится.

Подготовка необходимых данных входит в стоимость и время подготовки
результата. Эта сводка не определяет структуру `view`, модель пагинации,
универсальный формат элемента, новый метод или размещение по стеку.

## Оставшиеся решения

Применить выбранную основу нумерованного просмотра, сохранив перечисленные
выше требования приложения. Общие политики не образуют отдельную очередь
согласований внутри DAG-контракта.

Точные поля `results.view` и логического обращения за страницей, способ
представления места чтения и интеграция с источником ещё не определены.
Для подборки в них нужно выразить вхождения и их количество, сохранив
отдельный смысл счётчиков уникальных элементов DAG.
Точный запасной ориентир требует сведений о прежнем списке, не ограниченных
показанной страницей. Нужно обеспечить их доступность и оценить стоимость;
ослабление этого правила не принято.

Проверить стоимость прямого перехода по номеру, восстановления по элементу
и получения последней страницы для конкретного источника. На согласование
выносятся реальные расхождения готовой основы с принятыми требованиями,
а не каждый стандартный случай постраничного просмотра.
