# DAG-навигатор: допуск к миллионной ступени

Дата: 2026-09-24. Подготовка, не результат миллионного измерения.
Основа: `09a1b54`, [общий план](dag-navigator-scaling-experiment.PLAN.md),
[рост N до 100k](dag-navigator-scaling-growth-100k.md),
[рост полного ответа](dag-navigator-scaling-width-10k.md).

## Решение

**Прямое увеличение текущего задания до миллиона пока не допускается.**
Ограничить нужно не только индекс, но и проверочный стенд. Перед нагрузкой:

1. Разделить независимый эталон на непересекающиеся порции элементов,
   объединяя точные исходные сведения до сборки полного ответа.
2. Считать контрольную сумму и размер входа потоком, без единой большой
   строки `JSON.stringify(fixture)`; сохранить идентичность прежних checksum.
3. Проверить обновлённый протокол на прежних 100k, затем пройти ресурсные
   ступени 250k и 500k. Миллион запускать только при выполнении критериев ниже.

Алгоритмы `scan-source`, `index-source` и общий `navigation` не оптимизировать
одновременно с ростом N. Словарь остаётся 1000, назначений — 10 на элемент,
сохранённых фильтров — 100. V=10k с большим N не входит в эту серию.
Backend, транспорт, контракт и семантика полноты не меняются.

## Что установлено по имеющимся данным и коду

На 100k медиана **всего окна** независимой сверки `free/all` — 7,38 s;
это не чистое время запроса: окно включает подготовку и метаданные.
`extraTags` эталона отдельно перебирает элементы для каждого тега словаря,
а `count` — для каждого запрошенного набора. Проверка миллиона целиком
может превысить 30 s одного шага раньше, чем индекс исчерпает ресурсы.
Умножение 7,38 на 10 даёт ориентир около 74 s, **не измеренную задержку**
и не точный прогноз. Простое поднятие timeout не выбирается.

Рабочий процесс удерживает вход; каждый источник делает `structuredClone`
и канонизацию снимка. В verify одновременно живут вход, копия перебора,
копия индекса и сам индекс. Метаданные дважды последовательно вызывают
`JSON.stringify` всего входа: для SHA-256 и UTF-8 размера. GC не обязан
освободить временные объекты в удобный для стенда момент.

Ниже — **иллюстративная оценка**, не основание пропускать ресурсные ступени.
Взяты максимумы наблюдений на 100k и условная база runtime 49 MiB:
`R(1m) = 49 + 10 × (R(100k) − 49)`, затем переведено в GiB.

| Фаза | Измерено на 100k, MiB RSS | Линейный ориентир 1m, GiB | С запасом 25%, GiB |
| --- | ---: | ---: | ---: |
| После генерации | 172,34 | 1,25 | 1,57 |
| После построения индекса | 352,59 | 3,01 | 3,77 |
| Конец индексного задания с метаданными | 464,03 | 4,10 | 5,13 |
| Максимум verify с обоими источниками | 553,55 | 4,98 | 6,22 |

Память масштабируется не обязательно линейно; после GC и между фазами могут
быть пропущенные пики. Запас 25% — исследовательская эвристика, не гарантия.
Тем не менее уже эта грубая проверка не даёт достаточного запаса под
ориентир 4 GiB и watchdog 6 GiB для старой организации проверки.

При сохранении формата генератора вход миллиона занял бы **169 909 001 байт
UTF-8 JSON, около 162,04 MiB**. Это расчёт по размеру одной записи, длинам
ID, разделителям и неизменным узлам, без генерации миллиона. Формула дала
точно прежние 1 698 999 / 16 909 000 байт для 10k / 100k, seed 23.
Физическая память строки, копий и временных объектов не равна размеру JSON.

## Независимая полная сверка по порциям

Элементы разделяются по **уникальному ID**, не по тегам или подборкам:
каждый элемент ровно в одной порции. Все порции принадлежат одному
детерминированному снимку, а сохранённые фильтры общие для всего снимка.
Логический Interface источника остаётся прежним; порции — внутренний
протокол подготовки эталона, не новый интерфейс Навигатора.

Для выбранного AND-набора Q:

- Полное число элементов: сумма точных чисел по всем порциям.
- `extraTags(Q)`: объединение всех тегов из порций, для каждого — сумма
  точных частот. Теги Q исключаются; отсутствие в порции означает ноль,
  но отсутствие самой порции никогда не означает ноль.
- `count(sets)`: одна и та же последовательность канонических наборов
  во всех порциях; сложение по соответствующим наборам, без слияния
  пересекающихся подборок. Дедупликация тегов внутри элемента сохраняется.
- `related` и `collection`: вычисляются по полному общему списку подборок,
  не складываются и не ограничиваются подборками с ненулевыми результатами.
- Страница с offset O и limit L: из каждой порции взять первые O+L
  подходящих элементов в общем порядке ID, объединить, отсортировать,
  затем применить O/L **один раз глобально**. Элемент глобального префикса
  O+L не может иметь больше O+L−1 предшественников внутри своей порции,
  поэтому он не потеряется. `total` при этом суммируется независимо от страницы.

На миллионной ступени страница по-прежнему O=0/L=20; большие offset не
являются новой нагрузочной осью. Порядок строковых ID сохраняется: после
100k длина ID меняется, числовой порядок генерации нельзя выдавать за
строковую сортировку источника. ID не перенумеровывать ради разбиения.

### Последовательность подготовки эталона

1. Создать небольшой манифест снимка: профиль, seed, ревизия, узлы,
   непересекающиеся интервалы генерации, числа записей и checksum порций.
   Порог специальных тегов определяется **общим N**, не размером порции.
   PRNG продолжается через границы, а не перезапускается с seed для каждой.
2. В последовательных свежих процессах по <=100k элементов посчитать
   дополнительные теги каждого запроса. Суммировать полную карту.
3. По глобальной карте и полным сохранённым фильтрам составить наборы
   счётчиков: Q и все необходимые Q∪{tag} для `free`; Q и фильтры сохранённых
   потомков для `nodes`. Допустим проверочный наднабор запросов, но не
   выборочное покрытие. Теги только сохранённых подборок также включить.
4. Вторым проходом по тем же порциям получить точный полный пакет счётчиков
   и префиксы страницы. Использовать прежний независимый `scan-source`,
   без индекса, кешей кандидата или его результатов как эталона.
5. После проверки полноты манифеста предоставить объединённые сведения
   через прежний Interface источника и вызвать `readNavigation`.
   Сравнивать полный ответ, включая `sourceFacts`, а затем его digest.
   До завершения всех порций эталон не имеет исхода `ok`.

Контроль координатора: совпали ревизии, профиль/seed, checksum данных,
узлов и запросов; нет пропущенных/дублированных интервалов, разрывов или
пересечений; все записи охвачены ровно один раз. Повторный результат
порции не прибавляется дважды. Невалидный пакет или недоступное наблюдение
останавливают проверку, а не превращаются в частичный ответ.

Эта организация **не делает общий перебор быстрее** и не доказывает
распределённую масштабируемость продукта. Она разделяет проверочную работу
на ограниченные шаги. Полный индексный запрос остаётся единым измеряемым
чтением; его deadline нельзя сбрасывать на внутренних порциях.

## Что проверено в этой подготовке

[Малый proof-адаптер](../../prototypes/dag-scaling.PROTOTYPE/partition-proof.mjs)
реализует тот же Interface поверх нескольких независимых переборов;
[тесты](../../prototypes/dag-scaling.PROTOTYPE/partition-proof.test.mjs)
сравнивают результат с монолитным перебором. Максимум 100 элементов и
100 узлов, отказ до копирования больших массивов. Он синхронный и держит
все порции одновременно: **это проверка алгебры, не реализация будущих
последовательных worker и не доказательство их расхода памяти**.

TDD: сначала полный ручной сценарий, затем ограничение размера и крайний
offset. Зафиксированы red → green. Дополнительный регрессионный прогон:
50 пространств × 70 запросов × 2 режима × 3 размера порции = **21 000
совпавших полных ответов**. Есть пустое пространство, отдельный пустой узел,
нулевые сохранённые уточнения, теги только элементов/подборок, повторные
теги, несколько родителей, страницы со смещением, ревизии и защитные копии.
Дубли ID отвергаются до разделения. Общая логика `navigation` проверяется
прежними ручными ожиданиями: два источника с общей сборкой не являются
двумя независимыми реализациями всех правил Навигатора.

Результат подготовки: корректность композиции подтверждена на малых
фикстурах; потоковая генерация/метаданные, манифесты, IPC, повторы и
ресурсный контроллер нового протокола **ещё не реализованы и не проверены**.
Действующий нагрузочный runner по-прежнему запрещает N>100k.

## Условия допуска и остановки

Перед следующим нагрузочным шагом:

- Поток генератора и метаданных на 10k/100k должен совпасть побайтно/
  по SHA-256 с прежними данными, включая неполную последнюю порцию.
  На 100k новая полная сверка должна совпасть со старой на всех десяти
  запросах, без одновременного удержания двух полных больших источников.
- Отдельно испытать отсутствующую, повторную, пересекающуюся, неверную
  порцию, смену ревизии, повреждение checksum и сбой worker. Ни один
  такой случай не должен дать полный `ok`. Проверить общий deadline
  координатора, а не только таймер отдельно взятого процесса. Отдельно
  проверить страницу, когда строковый порядок ID переплетается между
  порциями генерации: малый proof разбивает уже канонизированный снимок.
- Сначала ограниченные допуски 100k → 250k → 500k на seed 23. Измерять
  генерацию, построение, чтения и метаданные, наблюдать все процессы.
  Не начинать следующую ступень после ошибки или остановки по ресурсу.
- Перед переходом Nprev → Nnext оценить память каждой фазы по текущим
  наблюдениям: `1,25 × [B + (Rprev − B) × Nnext/Nprev]`, где B — baseline
  того процесса. Взять максимум фаз и OS-наблюдений. Он должен быть <=4 GiB;
  иначе остановиться и пересмотреть стенд, а не опираться на старую оценку.
  Для непорционируемых шагов аналогичная временная оценка с запасом должна
  быть <=20 s. Это страховка перед запуском, не доказательство безопасности.
- Один активный worker; координатор не держит весь вход. Ориентир worker
  4 GiB, внешний RSS-watchdog 6 GiB, old space 4096 MiB, 30 s на шаг,
  120 s на worker, 10 MiB IPC/вывода. Наблюдать также координатор с пределом
  256 MiB; недоступное наблюдение запрещает продолжение. OS hard limit нет.
- Офлайн-эталон теперь имеет **явный суммарный бюджет 120 s на один полный
  эталонный запрос**, включая все его порции и оба прохода. Это изменение
  организации технической проверки, не обещание уложить её в прежний один
  шаг 30 s. Измеряемый индексный запрос по-прежнему ограничен 30 s целиком.
  Серия — не более 20 min под наблюдением; остановка сохраняет завершённые
  данные и явный исход, незавершённые точки не включаются в медианы.
- Перед каждым допуском и порцией — проверка read-only ресурсов:
  `memory_pressure -Q` доступен и system-wide free >=10%, диск >=1 GiB.
  Это не выделенный процессу ресурс. Старые файлы не перезаписывать;
  итоговый JSONL <=10 MiB, материализованный большой JSON не нужен.

После допусков — отдельная серия 100k/1m, seed 23/47/89, три процесса
индекса, первый ответ + прогрев + пять замеров на сценарий. Для среднего
seed порядок объёмов обратить. Ресурсные пробы не смешивать с этой серией.
Если бюджеты не позволяют выполнить протокол, записать конкретную границу
стенда и непроверенные точки. Не объявлять это потолком модели или backend.

## Состояние проверки

Перед тестами проверены импорты: только локальные вычислительные модули
и built-ins Node; `.env`, API/DSN, сеть, БД и установки не используются.
Read-only ресурсы при подготовке: 32 GiB RAM, около 765 GiB свободного
диска, `memory_pressure -Q` 63% system-wide free. Эти значения нужно
проверять заново перед нагрузкой. Миллион данных не генерировался.

Прогон:

```sh
env -u NODE_OPTIONS -u NODE_PATH node --test prototypes/dag-scaling.PROTOTYPE/rig.test.mjs prototypes/dag-scaling.PROTOTYPE/measurement.test.mjs prototypes/dag-scaling.PROTOTYPE/partition-proof.test.mjs
```

Полная проверка прошла: **49 тестов, 0 ошибок**, прежние 7000 и новые
21 000 сравнений ответов. Ни latency, ни RSS нового большого
протокола пока не измерены; внешняя производительность не экстраполируется.
