# DAG-навигатор: рост базы 10k → 100k при фиксированном словаре

Дата: 2026-09-23. Завершён второй локальный эксперимент в памяти.
Не SLA, не предел модели/продукта и не измерение backend с хранилищем.

## Результат

База выросла в 10 раз при прежних 1000 тегах и 100 сохранённых подборках.
Для полного «Всё» медиана индексного ответа выросла:

- в свободном режиме: **7,33 → 40,97 ms**, примерно в 5,6 раза;
- в режиме узлов: **0,209 → 0,216 ms**, практически без изменения
  на фоне субмиллисекундных расходов измерения.

Свободный ответ по-прежнему содержит все 1000 вариантов, около 127 KiB.
Время выросло в основном на подсчёте дополнительных тегов среди подходящих
элементов. Для узлов число сохранённых фильтров и переходов фиксировано,
а однотеговые счётчики берутся из длин готовых posting lists. Это различие
измеренной работы, не преимущество семантики одного режима над другим.

Все полные ответы на трёх seed совпали с независимым перебором. Ошибок,
таймаутов и остановок по ресурсам нет. Индекс не оптимизировался.

особенностями этого генератора. Несколько seed не превращают его в модель
всех пользовательских данных и не проверяют произвольные многотеговые запросы.

## Протокол и сопоставимость

Для каждого сочетания N и seed — полная сверка всех десяти ответов
с перебором, включая `sourceFacts`, переходы, счётчики и страницу. Сверка
разделена на шесть свежих процессов: пять `nodes` вместе, каждый `free`
отдельно. Это только техническое разделение разных запросов по окнам;
полнота одного логического ответа не сокращается.

После сверки — три свежих процесса **индекса**, каждый с теми же десятью
сценариями в прежнем порядке. На сценарий первое чтение, ещё один прогрев,
пять замеров. Перебор на этой ступени не получает повторных timing-серий:
его роль — проверка правильности. Длительность verify не выдаётся за latency
запроса и не сравнивается с прежними замерами перебора.

Всего 36 процессов сверки и 18 измерительных; 60 полных сравнений двух
источников, 900 измерений после прогрева, 180 первых чтений отдельно.
Все 1260 чтений индекса, включая дополнительный прогрев, сверены по digest
полного ответа. На ячейку таблицы — **45 замеров (3 seed × 3 процесса × 5)**.
Медианы по разным seed объединены только как описательная сводка; это
не оценка распределения реальных запросов. p95/p99 не публикуются.

Размеры попарно запускаются на каждом seed; для среднего seed порядок N
обращён, чтобы размер не был полностью спутан с порядком запуска. Хост
обычный интерактивный: load average перед точками 3,20–4,44, без закрепления
CPU и очистки кэшей. Один worker не означает жёсткую квоту одного CPU:
runtime, в частности GC, может использовать вспомогательные потоки.
Для исходного seed 23 новый `free/all` на 10k дал 7,39 ms против 7,10 ms
в первом пилоте; это показывает, почему не следует трактовать сотые ms
как стабильную характеристику продукта.

Определение времени прежнее: полный ответ и одна страница, с копированием
ответов источника и таймерами стадий, без подготовки, хеширования и JSON.
Сериализация и размеры сохранены отдельно. «Первое» — первое этого
сценария в процессе, не гарантированно холодный runtime/кэш. Принудительного
GC нет. Все RSS-снимки включают живой вход генератора, копию источника,
индекс, ответы и исследовательские накладные расходы.

Микросекундные различия в строках «один» и «нет совпадений» не означают,
что увеличение базы ускоряет решение. Накладные расходы, GC и прогрев
runtime здесь сопоставимы со временем самой операции.

Для `free/all` на 100k медианы по seed: **41,662 / 40,794 / 40,409 ms**.
Все 45 наблюдений: 39,755–58,274 ms; медиана первых чтений — 43,575 ms.
Это наблюдённый диапазон, не гарантия хвостовой задержки.

| Стадия `free/all` | 10k, медиана ms | 100k, медиана ms |
| --- | ---: | ---: |
| Сохранённые фильтры `related` | 0,066 | 0,065 |
| Дополнительные теги `extraTags` | 4,306 | 38,245 |
| Полный пакет счётчиков | 0,536 | 0,546 |
| Страница | 0,023 | 0,026 |
| Остаток сборки ответа | 2,066 | 2,054 |
| JSON и UTF-8 размер, вне `readMs` | 0,258 | 0,264 |

Медианы стадий не обязаны точно суммироваться в медиану целого. Здесь
`extraTags` перечисляет теги всех подходящих элементов; рост именно этой
стадии подтверждён замерами. Это свойство кандидата, не неизбежный предел
семантики: другие способы агрегации пока не сравнивались.

## Ответ и память — отдельные оси

Для `free/all` итоговый JSON: 129 627–129 656 → 130 551–130 567 байт
(около 126,6 → 127,5 KiB). Число вариантов постоянно; небольшая прибавка
связана с представлением больших счётчиков и метки ревизии. Исходные
ответы операций также сохранены отдельно; их нельзя складывать с итоговым
представлением как будто оба обязательно передаются по сети. Wire-формат
и размещение сборки по-прежнему не выбраны.

Фиксированный **общий** словарь не всегда фиксирует ответ конкретного среза:
для `free/one-percent` он вырос с 568–590 до 998–999 вариантов, JSON —
с 81 145–84 137 до 139 915–140 045 байт. При большем числе подходящих
элементов встречается больше разных тегов. Поэтому рост времени этой
строки нельзя приписывать только длине posting lists при одинаковом ответе.

| Подготовка / ресурс индексного процесса | 10k | 100k |
| --- | ---: | ---: |
| Генерация, медиана ms | 17,68 | 158,48 |
| Создание источника, медиана ms | 31,64 | 283,04 |
| RSS после создания, MiB | 90,67–91,23 | 350,94–352,59 |
| Максимумы наблюдённого RSS по процессам, MiB | 137,44–149,58 | 461,97–464,03 |

Создание источника включает копирование/нормализацию снимка и построение
обычных JS posting lists. Это не цена записи одного элемента и не физический
размер индекса. На 100k RSS в сохранённых точках после чтений достигал
371,23–373,66 MiB; самая большая сохранённая точка — конец технического
подсчёта метаданных, где стенд также хеширует и сериализует весь вход.
Нельзя приписывать весь рост до 464 MiB индексу. Отдельный процесс сверки,
сразу с обоими источниками, достигал 553,55 MiB по наблюдениям.

Наблюдение раз в 250 ms и снимки между фазами могут пропустить короткий
пик. Ни эти числа, ни их линейная экстраполяция не гарантируют потребность
миллионного профиля. Перед ним важны и временные копии/метаданные стенда,
а не только полезные структуры источника.

## Безопасность и проверки

Перед тестами и серией проверены entry point/импорты: только синтетическая
память и стандартные модули Node, никаких API/DSN, `.env`, сети, контейнеров
и БД. Worker получает пустое окружение. Read-only `/bin/ps` наблюдает только
процессы самого стенда, `/usr/bin/memory_pressure -Q` — состояние машины.
Sandbox-исключение требовалось для `ps`. Контракт и принятый UI не менялись.

Перед каждым профилем записаны ресурсы: около 768 GiB диска, `memory_pressure`
51% system-wide free; это не обещание свободной памяти конкретному процессу.
Серия отказалась бы начинать профиль при показателе ниже 10%, недоступном
наблюдении или диске меньше 1 GiB. Это исследовательская страховка.
На worker сохранены 30 s на шаг, 120 s на процесс, RSS-watchdog 6 GiB,
old space V8 4096 MiB (не весь heap/RSS); файлу серии — 10 MiB.
Жёсткой OS-квоты RSS нет. После первой ошибки серия прекращается и сохраняет
явный исход. Старые файлы открываются только на чтение, новые — через `wx`.

TDD добавил проверку сохранения 10k-checksum, профиля 100k, выборочных окон,
их покрытия и отказа при невалидном окне/недостающем эталоне. Вместе со
старым стендом **41 тест passed**, включая 7000 малых полных сравнений.
Smoke завершён; основная серия — 54 `ok`, 0 неуспехов, 112,6 s суммарно.
Самое долгое окно сверки — 7,39 s. JSONL — 798 683 байта. Сырые замеры,
digest всех сохранённых ответов, покрытие сценариев и хеши кода проверены.

## Что это позволяет сказать и что дальше

На этом статическом профиле **100 тысяч элементов не стали препятствием
для точного полного чтения в памяти**. Самый тяжёлый измеренный сценарий
занимает около 41 ms в медиане, но это не обещание задержки backend:
хранилище, сеть, очередь запросов, записи, ревизии при записи и множество
пользователей ещё не участвовали. На миллион и дальше эти числа не переносим.

Следующая отдельная ось — **рост словаря и полного числа вариантов при
фиксированных 10k элементов**, чтобы сравнить с уже измеренной исходной
точкой и не смешивать два источника роста. Пробный словарь до 10k, фактическое
покрытие и размеры фиксировать, полноту не ограничивать. Это ограниченный
шаг перед более тяжёлыми объёмами/хранилищем; его пределы времени и памяти
сначала оценить. Миллионная ступень остаётся в плане, но требует отдельного
бюджета и учёта накладных расходов проверочного стенда.
