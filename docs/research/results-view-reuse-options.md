# Переиспользование общей пагинации

Дата проверки: 2026-10-12. Подход к переиспользованию принят пользователем:
использовать подходящую готовую модель и описывать отличия приложения.
Позднее в тот же день [модель TanStack Table v8 принята для нумерованного просмотра](../../.scratch/dag-navigation-lab/issues/23-define-results-view-contract.md#принята-модель-tanstack-table-v8-для-нумерованного-просмотра--2026-10-12).
Библиотечная зависимость и стек не выбраны, Relay остаётся рассмотренной
альтернативой, а не второй обязательной основой. Ниже — факты проверки
и рекомендация, предшествовавшая выбору.

## TanStack Table v8: готовая логика номерных страниц

Это headless-библиотека для JS/TS: предоставляет состояние, вычисления
и операции, но не готовую разметку или оформление.
[Introduction](https://tanstack.com/table/v8/docs/introduction).

Состояние пагинации — `pageIndex` с нуля и `pageSize`. Есть переходы
вперёд/назад, к первой/последней странице и по индексу. Клиентская модель
разбивает весь переданный набор; `manualPagination: true` принимает уже
подготовленную страницу. Общее число страниц задаётся через `pageCount`
либо вычисляется из переданного `rowCount`. Следовательно, включение
серверного режима само по себе не реализует получение данных на сервере.
[Pagination Guide](https://tanstack.com/table/v8/docs/guide/pagination).

При изменении данных/фильтра по умолчанию сбрасывается индекс; ручная
пагинация отключает этот автоматизм. В исходниках сброс возвращает
настроенный начальный индекс, обычно `0`; пересчёт клиентской сортировки
тоже вызывает сброс. Смена размера сохраняет порядковую позицию прежней
верхней строки формулой `floor(oldPageIndex * oldPageSize / newPageSize)`.
Это позиция, а не поиск прежнего элемента по ID.
[RowPagination](https://github.com/TanStack/table/blob/v8/packages/table-core/src/features/RowPagination.ts),
[getSortedRowModel](https://github.com/TanStack/table/blob/v8/packages/table-core/src/utils/getSortedRowModel.ts).

Сортировка описывается списком `{ id, desc }`. При серверной пагинации
клиентская сортировка упорядочит лишь загруженные строки; `manualSorting`
ожидает уже отсортированные данные. Первое направление переключения
по умолчанию — возрастание для строк, убывание для чисел; настройки изменяемы.
[Sorting Guide](https://tanstack.com/table/v8/docs/guide/sorting).

Лицензия MIT разрешает использование, копирование и изменение кода;
при копировании сохраняются уведомления об авторстве и разрешении.
[LICENSE](https://github.com/TanStack/table/blob/main/LICENSE).

## Relay Cursor Connections: готовый контракт курсорной выдачи

Спецификация GraphQL задаёт `edges { node, cursor }` и `pageInfo`;
курсор непрозрачен клиенту. Продолжение вперёд задаётся `first/after`,
назад — `last/before`; реализация обязана поддерживать хотя бы одно
направление. `pageInfo` содержит `startCursor`, `endCursor`,
`hasNextPage`, `hasPreviousPage`. Признак наличия страницы в противоположном
направлении при определённых запросах допускает `false`, если его
дорого устанавливать. Порядок остаётся одинаковым при движении в обе стороны.
[Connections specification](https://relay.dev/graphql/connections.htm).

Бизнес-порядок и дополнительные аргументы оставлены приложению.
В обязательных полях нет общего количества и номера произвольной страницы.
Спецификация описывает результат и алгоритм среза, но не выбирает БД,
индексы или механизм согласованности при изменениях. Вывод: курсорный
контракт сам по себе не доказывает масштабируемость конкретного backend.
[Arguments and algorithm](https://relay.dev/graphql/connections.htm#sec-Arguments),
[Connection fields](https://relay.dev/graphql/connections.htm#sec-Connection-Types.Fields).

## Рекомендуемая граница заимствования

Для номерных страниц можно принять TanStack как образец поведения,
а подключение библиотеки отложить до выбора стека. Для курсорного доступа
можно взять модель Relay как образец; буквальное соответствие спецификации
означает GraphQL-контракт, установка Relay runtime из неё не следует.
Это разные модели доступа, не взаимозаменяемые названия поля `page`.

В принятом подходе заимствуется подходящая модель, описываются
отличия приложения. Здесь уже принято
[сохранение места по ID при обновлении](../concepts/selection-hierarchy/results-view-contract.DRAFT.md#уже-принятые-правила-текущего-приложения):
его нельзя заменить автоматическим сбросом TanStack или считать
обеспеченным одним курсором Relay. Выбор между номером и курсором и способы
реализации согласования страниц с ревизией и восстановления места остаются
отдельными решениями; принятые требования не пересогласуются.
Общие детали необязательно проектировать с нуля.

## Совместимость TanStack v8 с принятыми правилами приложения

Сверка ограничена кандидатом для номерного UI. Основания требований:
[правила хоста](../concepts/selection-hierarchy/dag-navigator-contract.DRAFT.md#7-правила-хоста-результатов),
[идентичность и готовность элементов](../concepts/selection-hierarchy/results-view-contract.DRAFT.md#данные-элемента-выдачи).
«Собственная интеграция» ниже — вывод из сопоставления этих требований
с областью документированных возможностей библиотеки.

| Требование | Покрытие и остающаяся работа |
| --- | --- |
| Обычные переходы между страницами, изменение размера | **Встроена логика:** `nextPage`, `previousPage`, `setPageIndex`, `setPageSize`, проверки доступности переходов. Кнопки и отображение предоставляет приложение. [Pagination](https://tanstack.com/table/v8/docs/guide/pagination), [headless](https://tanstack.com/table/v8/docs/introduction). |
| Управляемые подготовленные страницы и порядок | **Настраивается извне:** `state.pagination`/`onPaginationChange`, `state.sorting`/`onSortingChange`, `manualPagination` и `manualSorting`. Источник передаёт уже отсортированную страницу и количество; получение данных остаётся интеграции. [Pagination](https://tanstack.com/table/v8/docs/guide/pagination), [Sorting](https://tanstack.com/table/v8/docs/guide/sorting). |
| Новый фильтр → начало; обновление того же фильтра → сохранение места | **Настройка плюс интеграция:** отключить общий автосброс, различать причины изменения и явно задавать индекс. Автосброс библиотеки не выражает это различие; в ручном режиме он уже отключён по умолчанию. [Pagination](https://tanstack.com/table/v8/docs/guide/pagination#auto-reset-page-index). |
| Ориентир по ID, исчезновение элемента | **Собственная интеграция:** найти страницу с прежним ID; при исчезновении — со следующим сохранившимся в прежнем порядке, затем ближайшим предыдущим, затем начало; при пустоте страниц нет. Пересчёт индекса по размеру и сохранение номера этого не обеспечивают. [RowPagination](https://github.com/TanStack/table/blob/v8/packages/table-core/src/features/RowPagination.ts). |
| Страница, количество и DAG из одного снимка; ожидание и ошибки | **Собственная интеграция:** готовить и применять согласованный комплект, сохранять прежний при фоновом сбое, отличать ошибку/ожидание от пустоты. **Не гарантируется** одной передачей `data`/`rowCount`: библиотека ожидает уже подготовленные данные. [Manual pagination](https://tanstack.com/table/v8/docs/guide/pagination#manual-server-side-pagination). |
| Адаптивный размер из площади хоста | **Настраивается извне:** хост рассчитывает размер и передаёт его библиотеке. Формула смены размера сохраняет прежнюю порядковую позицию; при изменившемся составе нужен поиск по ID. [RowPagination](https://github.com/TanStack/table/blob/v8/packages/table-core/src/features/RowPagination.ts). |

Рекомендация: рассматривать TanStack как механизм страниц внутри общей
координации результата. Основные пробелы — поиск ориентира и согласованная
подготовка данных. Стоимость их реализации неизвестна. Это документальная
сверка без бенчмарка и проверки выполнения; библиотека не выбрана,
новые политики не приняты.
