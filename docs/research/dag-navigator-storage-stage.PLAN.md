## Зачем следующая проверка

Статические in-memory числа не отвечают на вопросы о цене настоящего
хранения, обновления индексов и согласованного чтения одновременно с записью.
Нужны D1 без записи и D2 с заданными 10 изменениями/с; затем тот же
адаптер/окружение используются для C1/C2. Новую СУБД или отдельную
реализацию под каждый профиль не готовить.

## Изоляция до любого интеграционного теста

Создать отдельный именованный контейнер с меткой
`org.collections.experiment=dag-storage-v1`, фиксированным локальным image ID,
`--pull=never`, `--network none`, без портов и host bind mounts.
Новые данные — на отдельном disk-backed volume; не tmpfs и не чужой volume.
До создания проверить отсутствие выбранных имени/volume, не заменять
совпавший ресурс автоматически. Не использовать существующий сервер.

Предлагаемый транспорт для малой проверки — постоянный процесс `psql -X`
через `docker exec` и локальный Unix socket внутри контейнера, без DSN
из окружения и без нового npm-пакета. Один процесс/соединение обслуживает
много запросов; запуск `docker exec`/`psql` заново на каждый SQL недопустим
как скрытая часть «скорости БД». Его стоимость и служебный транспорт
отдельно от SQL/полного чтения. Это исследовательский транспорт, не HTTP.

Защита перед работой: сверять container ID, image ID, метку, отсутствие
портов/host mounts, `NetworkMode=none`, явные имя базы/роль и собственный
маркер стенда в БД. Несовпадение — отказ, не попытка создать таблицы
по доступному адресу. Тесты не должны наследовать `.env`, `PG*`, shell
или Node preload-параметры. Данные только синтетические.

Перед запуском уточнить лимиты в исполняемом паспорте. Рабочий ориентир:
PostgreSQL 2 CPU / 3GiB, RSS адаптера до 768MiB и координатора до 256MiB,
файлы стенда до 10GiB, полный запрос до 30s, измерительное окно до 120s.
CPU-квота относится к контейнеру; CPU адаптера на хосте учитывается отдельно,
поэтому это **не обещание общей квоты 2 CPU**. RSS и размер heap различать.
Не очищать системный кэш, не отключать WAL/fsync и не поднимать лимиты
после неудобного результата. Не оставлять длительный прогон без наблюдения.

## Один проверяемый вариант адаптера

Следующее — проект исследовательского варианта, ещё не измеренный результат:

- Элементы/подборки принадлежат явному `spaceId`; уникальность ID и фильтра
  действует внутри пространства. Канонизация тегов и правила навигации
  прежние. Массив тегов + GIN — один кандидат, без перебора схем хранения.
- Начало полного чтения открывает короткую `REPEATABLE READ READ ONLY`
  транзакцию. Ревизия, связанные подборки, дополнительные теги, пакет
  счётчиков и страница принадлежат одному снимку. Снимок закрывается
  до возвращения готового ответа; не живёт между действиями человека.
- Счётчик ревизии — одна строка на пространство, не глобальная строка
  и не sequence. Изменение данных, ревизии и записи журнала стенда —
  одна транзакция. Стоимость конкуренции за строку учитывается, не считается
  бесплатной. Числовой порядок служебный, не свойство публичной ревизии.
- Новое чтение с недоступной прежней ревизией возвращает явный исход,
  а не новые данные со старой меткой. Хранение исторических снимков
  этим кандидатом не реализуется. Начатое чтение не смешивает изменения.
- Запись обеспечивает тестовые изменения элемента/его тегов и подборки;
  это не редактор данных Навигатора. Обновления не обходят его семантику.
- Полный логический ответ проверяется против прежнего независимого
  эталона и ручных малых примеров. Не грузить всю БД в in-memory индекс
  перед каждым запросом и не выдавать этот обход за чтение PostgreSQL.

Версионные основания и ограничения механизмов —
[заметка по первоисточникам](dag-navigator-storage-primary-sources.md).
Read-only снимок не доказывает корректность произвольных конфликтующих
бизнес-транзакций, а две серии не доказывают горизонтальную масштабируемость.

## Границы тестов и ближайший шаг

По TDD до новых тестов предложены пользователю три наблюдаемых поведения:

1. Полный ответ обоих режимов совпадает с эталоном, включая пустые фильтры,
   промежуточные наборы, несколько родителей, нули и явные исходы ошибок.
2. Запись данных/ревизии атомарна; начатое чтение согласовано, новое видит
   подтверждённые изменения; откат не публикует изменение и новую ревизию.
3. Стенд отвергает постороннюю БД/контейнер до любых изменяющих действий.

После предложения границ пользователь ответил «Продолжай» — продолжаем
с указанными тремя границами. Следующий шаг — один малый сквозной
red→green на полном ответе и защитах, затем атомарность/чтение при записи.
Малые проверки правильности не являются новыми измерительными профилями.

Малый адаптер завершён 2026-10-03: 5/5 тестов и 110 полных сравнений с
scan-эталоном. Проверены оба режима, Unicode, независимые пространства,
согласованный снимок при записи, атомарный откат данных/ревизии/журнала.
Собственный контейнер `collections-dag-storage-v1`, ID
`c9e58c46823388e8c7a2813ff8bea93b862027e6cbf01f404de42814ececd5b1`,
с volume `collections-dag-storage-v1-data` создан без сети/портов/host mounts.
Сервер 17.10, 2 CPU / 3GiB, fsync/synchronous_commit on, GIN fuzzy limit 0;
statement/transaction/lock/idle-in-transaction timeout — 20s/30s/2s/10s.
После тестов остановлен штатно (exit 0); данные сохранены. Продуктовые
DSN не использованы, ничего не скачивалось. Малые данные около 7,83MiB
всей БД — не результат масштабирования.

Перед D1 требовались порционная атомарная загрузка, подтверждаемая остановка
backend после timeout и ресурсное наблюдение; выполнено, 10/10 тестов.
Принят паспорт D1 с основной
N=100k/V=1k/M=100/k=10 и оценкой подготовки/полной сверки, без нового
промежуточного нагрузочного масштаба: все R1–R4 уже использованы.
Если допуск основного профиля не проходит — сохранить пробел, не повышать
лимиты и не подменять N. Точные расписания D2/C уточняются по цене D1;
подготовленные данные/индексы переиспользуются, затраты восстановления
между сериями записываются отдельно.

### Допуск D1, 2026-10-03

Порционная атомарная загрузка, отмена, серверный timeout и очистка захваченного
сеанса проверены: 10/10 малых тестов. Источник перед каждым соединением
проверяет фактический локальный target; сеть/порты/host mounts отсутствуют.
Код основного статического эталона (`contract/navigation/scan-source`)
сохранил SHA256 журнала `growth-10k-100k-2026-09-23.jsonl`. Для того же
N=100k/seed23/k10 имеется проверенный корпус SHA256
`9e5de82f16c99271dd446994c4872a71cdfd36f48288a8fea113c40a3602141c`
и полные независимые ответы. Их разрешено переиспользовать, лишь если новый
корпус совпадёт целиком: повторять дорогую сверку двух старых in-memory
кандидатов нет необходимости. Дополнительно весь загруженный корпус
проверяется количеством и MD5 от упорядоченных MD5 документов; это служебная
проверка корпуса, не криптографическое доказательство и не схема ревизий.

Исходный JSON 16 909 000 bytes / миллион назначений тегов; запас 20× к его
размеру даёт около 323MiB против лимита volume 10GiB. Это грубая оценка
допуска, не измеренный размер PostgreSQL. Память прежней полной сверки того
же корпуса укладывалась в 768MiB; новый адаптер отдельно наблюдается. Цена
SQL/GIN-загрузки пока неизвестна: допуск не обещает её время. Один load —
101 порция по <=1000 записей, одна транзакция до 30s; statement до 20s.
Индекс уже существует на малых данных и обновляется при загрузке, не
отдельно строится после неё; load включает эту работу, ANALYZE учитывается
отдельно. Запросы не используют промежуточный масштаб или скрытый top-N.

Один подготовленный корпус/GIN затем обслужит три свежих соединения:
каждое — nodes/free × «Всё»/10%-срез, первое чтение + один прогрев + пять
основных повторов. Это 60 основных наблюдений и 84 проверки полных ответов.
Кэши БД/ОС не сбрасываются; три соединения не являются независимыми
подготовками БД. Первая группа также следует после load/ANALYZE/проверки
корпуса и не называется холодной. Отклик включает локальный psql-транспорт
и закрытие снимка; таймеры методов — не чистое время SQL.

Прежний `runObservedJob`: 30s на фазу, 120s на worker, RSS адаптера 768MiB,
координатора 256MiB. PostgreSQL ограничен 3GiB/2CPU; примерно раз в секунду
считываются CPU/cgroup memory charge (включая cache, не RSS), OOM и volume.
При отказе worker захваченный PID + время старта + роль/база/app проверяются
и сеанс завершается; отсутствие backend подтверждается. Отказ до захвата
сеанса требует отдельного аудита, дальнейшие измерения прекращаются.
На хосте перед допуском 66% memory free и около 765GiB диска; volume до
загрузки около 46,7MiB. Один журнал создаётся с exclusive-create, без
перезаписи. D1 прекращается при первом отказе, лимиты не повышаются.

Пакет хранилища/изменений — 25 единиц. Подготовка3, малый адаптер6,
безопасная загрузка/надзор/D1/аудит/отчёт8: расход17, остаток8.

## Допуск D2, 2026-10-03 — зафиксирован до основного запуска

Тот же контейнер/volume/адаптер, корпус `data-D1-20261003-v1` и GIN из D1.
Повторного load, ANALYZE, очистки pending list/кэшей или изменения настроек
нет. После штатного запуска сохранённого контейнера проверены image/метка,
локальный socket, отсутствие сети/портов/host mounts и чужих клиентов.
Исходная ревизия `pilot-100000-23`, seq0; количество/отпечатки всех
100000 элементов и 100 подборок совпали с D1. Код D1 и журнал защищены
проверкой прежних SHA256. Другие окружения/DSN не используются.

Две новые малые проверки: независимый индекс с поправками на изменённые
записи сверяется с scan-эталоном; запись/чтение/пачка/восстановление — с
полными ответами на отдельном синтетическом пространстве. Это проверки
корректности, не пятый дополнительный масштаб. Общий малый набор повторён
для получения сохранённого итога: вывод предыдущего общего запуска утрачен
при сокращении контекста, он не засчитывается как подтверждённый результат.

Расписание основной серии:

- Три окна на одном подготовленном корпусе, одном writer и одном reader.
  Один независимый in-memory индекс готовится **один раз на все окна**;
  поправки учитывают только изменённые записи. Не строить его при каждом
  запросе/коммите. Цена подготовки и последующей сверки учитывается отдельно.
- В каждом окне 100 транзакций по одному существующему элементу, моменты
  поступления 0…9,9s с периодом100ms. В10s одна атомарная пачка:20 других
  элементов + название одной подборки. Затем запись прекращается.
  Число элементов, словарь, число подборок и тегов на элемент сохраняются:
  N100k/V1k/M100/k10, seed23. Не вставлять/удалять основной корпус.
- Один последовательный reader,12 запросов в моменты0…11s с периодом1s:
  nodes/free × «Всё»/10%-срез циклически. Если чтение не успевает, очередь
  измеряется, запросы не пропускаются. D1 дал широкий диапазон свободного
  чтения после загрузки/обслуживания: около2s…0,11s; выбор1Hz не опирается
  только на лучшую группу и не означает доказанную пропускную способность.
- Перед окном — полная сверка узкого свободного ответа; после расписания —
  один полный свободный запрос для проверки догоняющего чтения. Итого
  14 полных сравнений/окно,42/серия. Ответ сверяется с независимым состоянием
  **его** ревизии, включая страницу, счётчики, подборки, переходы и полноту.
  Журнал SQL сверяется с независимо запланированными операциями.
- Записываются заданные/фактические моменты и задержка очереди writer/reader,
  время подтверждения записи/чтения, ревизии и достижение итоговой ревизии
  после остановки записи. Это измерение периодических полных чтений,
  **не** проверка уведомлений, debounce, браузера или обещание SLA свежести.
- После каждого окна120 исходных элементов и название подборки возвращаются
  двумя транзакциями ≤100 операций. Отпечатки всего корпуса проверяются;
  восстановление — новая журналируемая запись, seq не откатывается.
  Ожидается103 коммита/окно и309 в конце, включая6 восстановительных.
  Время окна включает сверку/восстановление; их не выдавать за рабочую нагрузку.

Сохраняются пределы D1: PostgreSQL2CPU/3GiB, fsync/synchronous_commit on,
таймауты20/30/2/10s; worker768MiB/120s, фаза30s, координатор256MiB,
volume10GiB. Общий наблюдатель и подтверждаемая очистка обоих собственных
сеансов. Первый отказ прекращает серию; без повышения пределов, уменьшения
корпуса или автоматического повторного измерения. Журнал exclusive-create.
Перезапуск контейнера не гарантирует холодный кэш. Ресурсы контейнера
включают фоновые процессы/psql/cache; CPU адаптера на хосте вне его квоты.
CPU за время чтения в совместном worker включает также работу writer.
