# Устранить ложный отказ надзора и завершить миллионную серию

Type: task
Status: resolved
Blocked by: 10

## Question

Можно ли надёжно отличить штатное завершение собственного worker от
потери RSS-наблюдения живого процесса, сохранить fail-closed и добрать
недостающую парную точку 100k/1m на seed 89 без повторения всей серии?

## Evidence

[Предыдущий эксперимент](10-measure-million-profile.md#answer) подтвердил
миллион на seed 23, 47, но остановился на 1m/89 с `rss-observation-failed`.
Последний worker: code 0, signal null, result, фаза done; живого процесса
после серии нет. Причина исключения `/bin/ps` в исторический JSONL не попала.

[Малый воспроизводитель](../../../prototypes/dag-scaling.PROTOTYPE/diagnostics/rss-exit.REPRO.mjs)
дал тот же симптом 12/120 раз на почти пустых процессах около границы
250 ms опроса: `RSS observation unavailable` для child, code 0 и result.
Это red-capable probabilistic repro, не готовый детерминированный тест.
Общие 56 тестов проходят, гонку не закрывают. Приоритеты проверки и
методические ограничения — в [отчёте](../../../docs/research/dag-navigator-scaling-million.md#технический-отказ-и-следующий-шаг).

## Scope

Wayfinder, diagnosing-bugs, codebase-design и TDD. Источник/полный ответ
и измерительное задание остаются seams; индекс не оптимизировать.

1. Усилить диагностическую запись target/code/message и границ завершения.
   Доказать конкретный жизненный цикл малого воспроизведения; не объявлять
   все недоступные RSS нормальным выходом. По одному полученному result
   успех не возвращать: живой процесс без наблюдения и nonzero exit — отказ.
2. Регрессионный тест через настоящий supervisor; быстрый воспроизводимый
   сценарий выхода и отдельный отрицательный сценарий потери наблюдения
   действительно живого worker/координатора. Не ослаблять лимиты/deadline.
3. Сохранить старые результаты и хеши. Новый код — отдельная версия;
   повторно проверить обычные тесты и smoke, кандидат не меняется.
4. Подготовить и объявить отдельное ограниченное окно для недостающей
   пары 100k/1m, seed 89. Проверить текущие ресурсы и применимость старых
   допусков; если нужны промежуточные проверки, ограничить их явно.
   Каждый полный запрос всё ещё сверяется, без частичного успеха.
   Бюджет окна не увеличивать скрытно, прежнюю серию не перезаписывать.
5. Обновить отчёт с явным разделением серий, версий, failure и нового исхода.
   Только после завершения третьего seed объединять 45 замеров на ячейку.

Без сети, API, БД, установки, UI или записей пользователя. Новая ось роста
и продуктовая архитектура этим не выбираются. 10 миллионов не запускать.

## Work — 2026-09-24

Сохранены согласованные seams: явное измерительное задание и его ресурсный
допуск/расписание, источник и полный ответ. UI/индекс/эталон не меняются.
Малый repro перед исправлением дал 6/120 ложных отказов; дополнительное
OS-наблюдение поймало `?E 0` (exit flag, RSS 0) до события выхода Node.
Теперь после ошибки RSS собственного child проверяется состояние выхода
через `/bin/ps`; E/Z/отсутствие PID допускают только ожидание закрытия,
не успешный результат. Code 0 + полный result по-прежнему обязательны.
Живой child без наблюдения и ошибка координатора дают отказ; незавершённый
опрос учитывается даже при одновременном событии close. Сохраняется аудит
ошибки и состояния, старые лимиты не увеличены.

Регрессионный тест на старом надзоре падает, на исправленном проходит;
исходный probabilistic repro после исправления — 0/120. Все 63 теста и
новый smoke прошли. При подготовке теста устранена коллизия имён `.TEST`
и `.test` на case-insensitive томе; отдельные basename, оставшихся процессов
нет. Временная копия старого надзора для red-проверки удалена.

Отдельный режим `finish89` повторяет допуски 100k/250k/500k на seed 89,
затем пару 100k/1m по три индексных процесса и пять замеров. Старые допуски
не заимствуются вслепую после перерыва. Предел нового окна 20 min, полного
эталона 120 s, worker 30 s на шаг / 120 s всего, те же RSS/heap/output limits.
Новый файл `results/million-finish89-2026-09-24.jsonl`; первый отказ прекращает
окно, прежний failed-журнал остаётся неизменным. Запуск разрешён после smoke;
окончательный исход зафиксирован ниже.

## Answer

Миллионная серия завершена: новое окно 2026-09-24, сводка и аудит
зафиксированы 2026-09-26. Исправление различает переход собственного
worker к выходу и потерю наблюдения живого процесса, без повышения лимитов.
Регрессионный тест был red на прежнем надзоре; 63 теста прошли после
изменений и после нагрузочного прогона, исходный repro — 0/120.

Дополнительное окно: свежие допуски 100k/250k/500k и пара 100k/1m/89,
314 заданий `ok`, 50 полных сверок, 330 замеров, 90 первых чтений,
582,977 s, 889 102 байта, финальный `complete`. Один `exit-pending`
на порции эталона корректно дождался code 0 и полной проверки; диагностическая
запись сохранена. Ошибки живого процесса не маскируются результатом.

[Сводка трёх пар](../../../docs/research/dag-navigator-scaling-million-completed.md)
использует seed 23/47 из v1 и новую пару 89 из v2: 45 замеров на ячейку,
900 всего, первые чтения отдельно. Свободное «Всё»: 34,40 → 318,30 ms;
миллионный процесс максимум около 2,08 GiB RSS. Хеши источников, покрытие
порций, полные digest и неизменность старого failed-журнала проверены.
Это не потолок backend, QPS или гарантия свежести.

Следующий вопрос из шкалы — стоимость роста сохранённых фильтров;
[подготовка отдельного профиля](12-prepare-saved-filter-growth.md) вынесена
в следующий ticket. Здесь эта ось не запускалась, её точные параметры и
продуктовая архитектура не выбирались. UI, сеть, БД и продуктовые данные
не затронуты.
