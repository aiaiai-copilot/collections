# Устранить ложный отказ надзора и завершить миллионную серию

Type: task
Blocked by: 10

## Question

Можно ли надёжно отличить штатное завершение собственного worker от
потери RSS-наблюдения живого процесса, сохранить fail-closed и добрать
недостающую парную точку 100k/1m на seed 89 без повторения всей серии?

## Evidence

[Предыдущий эксперимент](10-measure-million-profile.md#answer) подтвердил
миллион на seed 23, 47, но остановился на 1m/89 с `rss-observation-failed`.
Последний worker: code 0, signal null, result, фаза done; живого процесса
после серии нет. Причина исключения `/bin/ps` в исторический JSONL не попала.

[Малый воспроизводитель](../../../prototypes/dag-scaling.PROTOTYPE/diagnostics/rss-exit.REPRO.mjs)
дал тот же симптом 12/120 раз на почти пустых процессах около границы
250 ms опроса: `RSS observation unavailable` для child, code 0 и result.
Это red-capable probabilistic repro, не готовый детерминированный тест.
Общие 56 тестов проходят, гонку не закрывают. Приоритеты проверки и
методические ограничения — в [отчёте](../../../docs/research/dag-navigator-scaling-million.md#технический-отказ-и-следующий-шаг).

## Scope

Wayfinder, diagnosing-bugs, codebase-design и TDD. Источник/полный ответ
и измерительное задание остаются seams; индекс не оптимизировать.

1. Усилить диагностическую запись target/code/message и границ завершения.
   Доказать конкретный жизненный цикл малого воспроизведения; не объявлять
   все недоступные RSS нормальным выходом. По одному полученному result
   успех не возвращать: живой процесс без наблюдения и nonzero exit — отказ.
2. Регрессионный тест через настоящий supervisor; быстрый воспроизводимый
   сценарий выхода и отдельный отрицательный сценарий потери наблюдения
   действительно живого worker/координатора. Не ослаблять лимиты/deadline.
3. Сохранить старые результаты и хеши. Новый код — отдельная версия;
   повторно проверить обычные тесты и smoke, кандидат не меняется.
4. Подготовить и объявить отдельное ограниченное окно для недостающей
   пары 100k/1m, seed 89. Проверить текущие ресурсы и применимость старых
   допусков; если нужны промежуточные проверки, ограничить их явно.
   Каждый полный запрос всё ещё сверяется, без частичного успеха.
   Бюджет окна не увеличивать скрытно, прежнюю серию не перезаписывать.
5. Обновить отчёт с явным разделением серий, версий, failure и нового исхода.
   Только после завершения третьего seed объединять 45 замеров на ячейку.

Без сети, API, БД, установки, UI или записей пользователя. Новая ось роста
и продуктовая архитектура этим не выбираются. 10 миллионов не запускать.
