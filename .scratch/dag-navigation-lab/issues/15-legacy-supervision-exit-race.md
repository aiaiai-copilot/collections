# Устранить гонку выхода в старом измерительном надзоре

Type: task

## Question

Как устранить ложный `rss-observation-failed` старого `runMeasuredJob`
при успешном выходе собственного worker, сохранив его Interface,
прежние отрицательные проверки и все ограничения ресурсов?

## Evidence

2026-09-27 до серии сохранённых фильтров все 78 тестов прошли. После
успешного завершения серии повторный общий прогон дал 77/78: старый
`measurement.test.mjs` (`isolated job verifies complete answers...`,
строка проверки статуса в цикле кандидатов) получил
`rss-observation-failed` вместо `ok`. Старый runner в этом этапе не менялся.

[Минимальный воспроизводитель](../../../prototypes/dag-scaling.PROTOTYPE/diagnostics/legacy-exit.REPRO.mjs)
сравнивает два надзора на крошечных собственных worker. Реальный `ps`
читается после OS-выхода, до обработки события Node. Старый runner
вернул ошибку при code 0 и полном `completed`; новый saved-filter runner
вернул `ok`, сохранив `exit-pending`. Асинхронный первый вариант чтения
`ps` не воспроизвёл окно; синхронное чтение после короткой блокировки
координатора даёт адресный сигнал. Исправление здесь ещё не выполнялось.

```sh
env -u NODE_OPTIONS -u NODE_PATH node prototypes/dag-scaling.PROTOTYPE/diagnostics/legacy-exit.REPRO.mjs
```

## Scope

Diagnosing-bugs, codebase-design, TDD. Сначала красная регрессия через
Interface старого задания, затем минимальное исправление/переиспользование
надзора без изменения исходных алгоритмов и исторических журналов.
Проверить живой child, nonzero exit, наблюдение в полёте и таймауты;
не получать зелёный результат повторением теста до удачного исхода.
Перед процессными тестами проверить локальную изоляцию, без API/БД/сети.

Новая серия `saved-pairs-measure-v1` уже использует исправленный надзор,
все 513 заданий успешны. Эта задача не требует повторять её или прежние
большие нагрузки. Не объявлять обнаруженный отказ пределом продукта.
